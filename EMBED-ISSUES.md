# Проблемы процесса работы с embed'ами

Свалка того, что всплыло при сборке `birch-mcp-usecases-embed` и `birch-mcp-statement-embed`
(июль 2026). Ничего из этого пока не чинится на уровне процесса — документ нужен, чтобы
не собирать те же грабли заново и чтобы было с чем сесть, когда дойдут руки.

Формат: **что случилось → почему → что с этим делать.**

---

## 1. Проверка шла в среде, не похожей на реальную

**Что.** Embed открывали напрямую (`embed/xxx.html`). У фрагмента нет `<!DOCTYPE>`, браузер
включает quirks mode. Там таблицы перестают наследовать `font-size` (UA-правило
`table { font-size: medium }`), и таблица в чате мерялась от 16px вместо `em`-шкалы карточки.
Полдня ушло на «баг», которого на сайте не существует.

**Почему.** Не было стенда, повторяющего условия Webflow.

**Сделано частично.** `debug/embed-harness.html?e=<имя>` — оборачивает embed в документ
с doctype, подключает `design-system/webflow-env.css`, слот намеренно `text-align: center`
(ловит протечку выравнивания).

**Осталось.** Харнесс не воспроизводит правила голых тегов с bir.ch (см. п.2). Их надо
вшить в харнесс как «враждебный» слой, чтобы такие столкновения ловились до вставки.

---

## 2. Сайт стилизует голые теги — и бьёт по любому embed'у

Проверено на `birch-testing.webflow.io`:

| правило сайта | что ломало |
|---|---|
| `h1…h6 { max-width: 400px }` | заголовки карточек упирались в 400px и переносились на 2 строки |
| `p, li, td, th { font-size: 14.4px }` | текст чата схлопывался в мелкий «табличный» вид |
| `ul { padding-left: 40px }` | списки уезжали вправо |
| секция с `text-align: center` | весь блок центровался |
| глобальный reset Webflow | срезал паддинги (нужен `!important`) |
| `.w-embed` во флекс-слоте | схлопывается в 0 |

**Важно.** Токены дизайн-системы на сайте **не объявлены вообще** — ни одного
`--text-*`, ни одного `--color-*`. Root font-size 16px.

**Осталось.** Решить принципиально: продолжать перекрывать теги руками (сейчас так) или
изолировать блок (shadow DOM). Изоляция закрывает класс проблем целиком, но если скрипт
упадёт, блок останется пустым — сейчас при падении скрипта текст хотя бы виден.

---

## 3. Стратегия токенов была неверной

**Что.** Писали `var(--token, литерал)` на каждое свойство. Для CSS работало, но:

- в разметке инлайном стоит `style="color: var(--color-text-grey)"` **без** фоллбека →
  переменной нет → объявление невалидно → цвет наследуется белым. Серые описания побелели.
- фоллбеки несли только десктопные значения, а `tokens.css` меняет шкалу на мобилке
  (`--text-h2-size` 3.25rem → 2rem). На телефоне заголовок остался 52px.

**Как правильно** (так сделано в одобренном `ai-promo-acc-embed`): объявлять **весь набор
токенов на корне embed'а**. Тогда ничего не течёт с сайта, инлайновые `var()` резолвятся,
а мобильную шкалу задаёт медиазапрос на том же корне.

---

## 4. Ловушки специфичности при защите от сайта

Дважды наступили на одно и то же:

- `.root p { margin: 0 }` — это (0,1,1), а `.acc-mob-e__eyebrow` — (0,1,0). Ресет тегов
  победил и **сплющил все отступы компонентов**. Лечится `:where()` — нулевая специфичность.
- Обратный случай: guard `max-width: none` (0,1,1) задавил собственный `max-width: 55.5rem`
  у заголовка (0,1,0). Пришлось поднимать правило компонента до (0,2,0).

**Правило.** В ресете на нулевой специфичности (`:where`) — только то, что компоненты
задают классами. В блоке реальной специфичности (0,1,1) — только свойства, которых
компоненты на (0,1,0) не трогают. Смешивать нельзя.

---

## 5. Сборка embed'а руками из dev-страницы ненадёжна

**Что происходило:**

- переименование классов регуляркой по всему файлу съело слово `account` в тексте вопроса
  («on the account-e overnight»);
- срез строк для скрипта потерял открывающую `(function () {` → скрипт не выполнялся
  вообще, молча, без ошибок в консоли;
- HTML-сущности (`&mdash;`) в JS-строках показывались буквально, потому что строка идёт
  через `textContent`, а не `innerHTML` → нужны юникод-эскейпы `—`;
- JS читает CSS-переменные (`--color-accent-*`) — на сайте их нет, `token()` возвращал
  пустую строку, и акцентные фоны исчезали. Нужна карта фоллбеков в самом скрипте;
- минификация CSS регуляркой разъехала вложенность; визуально выглядело нормально,
  поймали случайно.

**Осталось.** Для JS есть `node --check`. Для CSS проверки нет вообще — нужна хотя бы
сверка количества распарсенных правил до/после. И осторожно с CSSOM-пробами: в Chrome
с поддержкой CSS Nesting у обычного правила тоже есть `.cssRules`, наивный обходчик
пропускает всё и выдаёт бессмысленные цифры.

## 6. Лимит размера в Webflow

Эмпирика, не документация: `ai-promo-acc-embed` = 46 227 символов проходит,
52 878 — уже нет. Порог где-то около 50k.

Что помогло: вырезать комментарии (−21%, до ~42k). Источник правды остаётся в
`birch-mcp.html` и `design-system/`.

**Не сделано.** Мобильные слайды дублируют контент, который уже лежит в массиве `CHATS`.
Генерировать их скриптом — минус ~6–7k и заодно уходит дублирование текстов.

---

## 7. Дублирование как системная проблема

- Стили чата форкнуты по **8 файлам**. Общих селекторов 18, из них **17 с разными
  значениями**. Это не переиспользование, а восемь независимых копий с одинаковыми именами.
  Заведена отдельная задача на сведение к `design-system/components/chat-card.css`.
- Внутри `birch-mcp.html` тот же контент лежит **дважды**: статические мобильные слайды
  и массив `CHATS` для десктопного JS. Любую правку текста нужно вносить в оба места.
- Embed не может подключить `design-system/*.css` — он обязан быть самодостаточным,
  а билд-шага в репозитории нет. Значит дублирование структурное, а не по небрежности.

**Осталось.** Либо простой инлайнер (вставляет содержимое компонентного CSS в `<style>`
при сборке), либо жёсткая договорённость: править только общий файл, в embed копировать.

---

## 8. Процессное

- Собирали с нуля от dev-страницы, хотя уже существовал **одобренный аналог**
  (`ai-promo-acc-embed`), где были решены: блок токенов на корне, шкала ×0.9, ресет тегов,
  `!important` на паддингах, размер в лимите. Половину пунктов переоткрывали заново.
- Правила, которые уже записаны в `CLAUDE.md` (наследование `text-align`, `!important`
  на паддинги, `text-wrap: balance` на заголовки), не были перечитаны перед сборкой —
  и все три выстрелили.
- Дефекты находил дизайнер по скриншотам, а не проверка до отправки.

**Вывод для следующего раза:** стартовать от существующего одобренного embed'а, а не от
dev-страницы; перед сборкой перечитывать раздел про embed в `CLAUDE.md`; харнесс поднимать
**до** написания кода, а не после первых жалоб.
