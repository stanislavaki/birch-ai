# Версионирование юридических документов (`/legal/*`)

План переноса юр-документов из статичных страниц в CMS-коллекцию, чтобы у каждого документа
была история редакций: актуальная всегда по адресу без даты, прошлые — по адресу с датой,
переключение через селектор на строке `Effective date`.

редакций и записью-указателем, см. отдельный раздел ниже.

Структура тела одинаковая у всех пяти документов:

```

  p._14px.grey                                             ← «Effective date: …» ← сюда селектор
  .legal-rt.w-richtext                                     ← тело

  [.legal-rt.w-richtext]                                   ← продолжение тела после таблицы
```

`Opt Out` — лендинг с формой и canvas-анимацией, без даты и вне табов. В систему не входит.

### Что проверено по содержимому (важно для переноса)

- **Теги внутри rich text:** только `p`, `h3`, `h5`, `h6`, `ul`/`li`, `a`, `strong`, `em`, `br`.
  Всё это родное для CMS rich text — тела переезжают без разбора и пересборки.
- **Ни одного `id`-якоря и ни одной ссылки на `#раздел`** ни в одном документе. Это была главная
  опасность переезда (rich text не даёт ставить `id` на заголовки) — её нет.
- **Таблицы уже лежат в HTML embed**, а не в rich text. В CMS embed вставляется внутрь
  rich-text-поля (плюсик на новой строке в CMS-редакторе → HTML embed), то есть переезжает один-в-один.
  Формулировка «CMS rich text не умеет таблицы» неверна: нет *элемента* «таблица», но embed внутри поля есть.
- **Размеры:** максимум — DPA, 62 КБ после сборки тела. Лимит текстового поля Webflow порядка
  мегабайта, запас кратный.
- **Таблицы кладутся в тело обёрткой `<div data-rt-embed-type='true'>`** — см. `webflow-mcp.md`.
  Первая заливка ушла с `<div class="w-embed">` (разметка статичной страницы), и редактор показал
  таблицу простынёй текста вместе с CSS. Data API при этом вернул отправленное байт в байт: **эхо
  ответа не доказывает, что разметка распознана**, проверять надо в редакторе или на странице.
  **CSS в записи не лежит вообще.** Запись держит содержание, структуру и ширины колонок инлайном
  на `<col>`; всё общее (рамки, паддинги, кегль, скролл на мобилке) — один раз в кастом-коде
  шаблона, каноника в [`webflow/legal-template.head.html`](../webflow/legal-template.head.html).
  Обёртка `<div class="rt-table">` — единственное имя класса, которое несёт разметка; на сайте оно
  свободно, чужие таблицы (`.uc-table`, `.table` в use-cases) не заденет.

  Первоначально CSS оставался внутри embed'а «чтобы архивная редакция была самодостаточной» — это
  неверный размен: замораживать надо текст, а не толщину рамок. Иначе через пару лет на сайте живёт
  несколько поколений таблиц, и ни одну нельзя поправить разом. Два исходных блока CSS оказались
  идентичны с точностью до имён классов, ширин колонок и мобильного `min-width` (680 против 640,
  сведено к одному значению).
- **Заливка идёт мимо контекста агента.** Тела нельзя гнать через tool-вызовы: агент физически
  набирает 62 КБ юридического текста, и потерянную оговорку потом никто не заметит. Рабочая схема:
  отдельный Webflow API-токен с правами CMS read+write лежит в `~/.webflow-token` (не в репозитории,
  не в переписке), скрипты в скретчпаде читают страницы, собирают тела и шлют их напрямую в Data API.
  Существующий `sms-sites-token` не трогать: он read-only и на нём висит чужая живая интеграция.

## Решения (согласовано 22.09.2026)

- **Полный CMS.** Одна коллекция, и текущие, и архивные редакции — записи в ней. Причина: статичные
  архивы замораживают не только текст, но и обвязку (табы, селектор, типографика). Через три года это
  ~20 страниц, и любая правка стиля — двадцать раз руками.
- **Архив копится с сегодняшнего дня.** Текстов прошлых редакций нет, на старте по одной записи на
  документ, все `Is current`.
- **Архивы закрыты от индексации** (решение пересмотрено 22.09.2026). Сначала договорились не
  прятать и защищаться баннером — потому что поштучной настройки индексации в Webflow нет, а
  обходиться скриптом было дорого. Цена упала, когда появилось поле `Is archived`: теперь условие
  выражается видимостью, а она вырезает разметку целиком, так что скрипт внутри баннера существует
  только на архивных страницах. Механика — в `webflow-mcp.md`. Баннер при этом остаётся: он для
  того, кто пришёл по прямой ссылке, а `noindex` — чтобы недействующая редакция не всплывала
  в выдаче по запросу вроде «birch terms».
- **Селектор показывает все редакции**, текущая с пометкой.
- **Полей `summary of changes` и страницы-хаба нет.** Хаб (список всех редакций всех документов)
  нужен только под комплаенс-сценарий — аудитор просит историю изменений. Заводится за полчаса
  поверх той же коллекции, когда попросят.
- **`/legal/opt-out` → `/opt-out`** с 301, если префикс `legal` иначе не отдаётся коллекции.

### Как сверялся перенос (22.09.2026)

Две независимые проверки, обе прошли на всех пяти документах:

1. **Передача.** После заливки тела выкачаны обратно из CMS и сравнены с отправленными посимвольно —
   совпали (24 428 / 32 467 / 10 854 / 7 576 / 61 817 знаков).
2. **Сборка.** Видимый текст исходной страницы (без табов и строки `Effective date`) сравнён с
   видимым текстом собранного тела — совпал до знака (23 004 / 31 260 / 8 767 / 6 780 / 57 830),
   число ссылок и ячеек таблиц не изменилось.

Первая проверка одна ничего не доказывает: она сверяет отправленное с полученным, а не с оригиналом.
Потерю на этапе сборки ловит только вторая.

Решения по раскладке (согласовано 22.09.2026):

- **Шапка во всю ширину `.container`** (1408px), текст — своей колонкой. Вариант «всё в одной колонке»
  отклонён. Прежняя страница держала шапку в 1100px, так что верхний блок стал шире на ~300px.
- **Ширина колонки текста независима от `u-measure`** — намеренно, чтобы правка системного токена
  не двигала юр-документы. Значение `34.66rem` (610px): при теле 0,9rem это ~75 знаков в строке.
  Исходные 680px считались в паре с укрупнением тела до 1rem; кегль решили не трогать, поэтому 610.
- **Заголовок — тег `h1` с классом `.h2.u-position-relative`** (решено 22.09.2026 после просмотра
  в Figma). Дефолтный `.h1` давал 76,8px на окне 1280 — для юр-документа слишком парадно; `.h2`
  даёт 54,7px, что близко к 52px, которые дизайнер поставила в макете. Тег остаётся `h1`: меняется
  только визуальный класс, структура заголовков страницы не ломается. Комбо `u-position-relative`
  обязательно — базовый `.h2` абсолютно позиционирован, см. `webflow-mcp.md`.
- **Ритм.** Сверху секции распорка `.divider.s` (70px), снизу тела — `.divider.m`. А два отступа
  вокруг шапки — над заголовком и под строкой даты — заданы **паддингом на группе**
  `legal-head-group`, а не распорками: одно значение `3rem` в одном месте вместо двух элементов
  (решение дизайнера 22.09.2026). На 1280 это 48px; корневой кегль на сайте плавающий, поэтому
  на 1600+ те же `3rem` дают 57,6px — отступ масштабируется вместе с типографикой.
- **`main.page-main#main`** — тег `main` и id проставлены, так что на юр-страницах skip-link наконец
  работает. На остальном сайте он сломан, заведено отдельной задачей.

**Табы уже компонент** (`legal-menu-tabs`, без пропсов) — ряд не надо собирать из коллекции
`Legal document types`, он и так в одном месте и ссылается на `/legal/*`, что после катовера верно.

Комбо `.rich-text-base.rt-legal` заведено, несёт только `max-width: 38.6rem` (≈680px при корне 17,6px).

Порядок сборки через MCP: `data_style_tool > create_style` (комбо) → `data_element_builder`
(секции деревом, `children[]`) → `data_component_builder` (инстансы компонентов по имени).
Билдер элементов инстансы ставить не умеет — для них отдельный компонентный билдер.

### Селектор редакций (собран 22.09.2026)

Строка даты: `.legal-eff` (flex, по центру) = подпись `Effective date:` обычным текстом +
нативный Dropdown. Кликается только дата со стрелкой, подпись остаётся текстом.

Отступы взяты с `.filter-tab` со страницы `/how-to-choose-birch-ai-tools`: паддинг `1rem`,
радиус `0.75rem`, gap `0.375rem`, серый `#F1F0F7`. Список повторяет логику самого компонента
табов — серая подложка, активная строка белая.

- `legal-ver` — обёртка (`margin: 0`, иначе вебфлоувский `auto` растаскивает ряд)
- `legal-ver-toggle` — триггер; серый на `:hover`, `:focus-visible` и `.w--open`
- `legal-ver-list` — список; **без `display`** в классе, иначе раскрыт всегда. Фон и размытие
  взяты у выпадающего меню нава: `rgba(211, 209, 224, 0.4)` + `backdrop-filter: blur(30px)
  saturate(0.8)`. Вебкит-префикс Webflow дописывает сам — задавать его руками не нужно, тул такое
  свойство и не принимает. `margin-top: 0.25rem` отделяет список от триггера.
- `legal-ver-item` — строка; радиус **4px**, не 12: внутренний радиус сопрягается с внешним по
  правилу «внешний минус паддинг» (12 − 8 = 4), иначе углы строки и панели не совпадают по кривизне
  и это видно. Шаг между пунктами 8px. Ховер и фокус дают полупрозрачный белый (50%), открытая редакция —
  сплошной белый по классу `.w--current`, который Webflow ставит сам. Покрасить его состоянием
  в панели стилей **не вышло**: в списке состояний ссылки есть «Current Locale», и правило из него
  в опубликованный CSS не попадает. Поэтому строка живёт в кастом-коде шаблона рядом с `.w--open`.
- `legal-eff-label` — комбо на подписи «Effective date:»: тот же вертикальный паддинг, что у плашки,
  и обнулённые маргины. Нужно для совпадения базовых линий, разбор — в `webflow-mcp.md`.

**Решения по разметке селектора (22.09.2026):**

- **Маркера «действующая редакция» в селекторе нет.** В макете была точка 6×6 рядом с датой, но её
  сняли: она путается с состоянием «открытая страница», а признаков в одном списке должно быть не
  больше одного. Какая редакция в силе, сообщает баннер архивной страницы со ссылкой на неё —
  информация не теряется, а селектор отвечает ровно на один вопрос: «где я».
- **Состояний строки два:** ховер и фокус — белый на 50% прозрачности, открытая редакция — сплошной
  белый через нативное `w--current`.

**Баннер архивной редакции** `legal-archive-note` над телом: ширина текстовой колонки (34.66rem),
серый `#F1F0F7`, паддинг 1rem, радиус 0.75rem, текст по левому краю. Видимость — по `Is archived`.

Текст одной строкой: «You're viewing an archived document. **See the current version →**». Даты
в баннере нет намеренно — она стоит прямо над ним, в селекторе.

**Цвет ссылки — `Secondary/Indigo` (#4551f2), без подчёркивания.** Токен с именем «синий» в палитре
есть — `Secondary/Lignt Blue` #59dbff, — но на сером фоне баннера он даёт контраст **1,43:1** при
пороге AA 4,5:1, то есть нечитаем. Indigo даёт 5,0:1. Правило на будущее: цвет ссылки выбирать
не по имени токена, а по замеру контраста на том фоне, где он окажется.

Ссылка живёт внутри отдельного Collection List (сортировка по дате вниз, лимит 1), потому что ведёт
на **другую** запись — действующую редакцию того же документа. Этому списку **нужен фильтр по типу
документа**, иначе он покажет самую свежую редакцию по всей коллекции, а не по этому документу.

**Поле `Is current` заменено на `Is archived`** (22.09.2026; 23.09.2026 заменено на `Status`, см.
«Статусы редакций и запись-указатель» — там же причина, почему одно поле, а не набор свитчей). После отказа от точки у `Is current`
не осталось ни одного потребителя, а условная видимость через API умеет только «показать, когда
свитч включён» — отрицания нет. Перевёрнутое по смыслу поле делает условие баннера выразимым
через API, то есть воспроизводимым при пересборке шаблона, без настройки, которую надо помнить.

**Документ с одной редакцией.** Селектор в этом случае бессмысленен, поэтому превращается в обычный
текст: `:has(.w-dyn-item:only-child)` гасит стрелку и снимает кликабельность. Условия «в списке
меньше двух элементов» в Webflow нет — считать он не умеет, поэтому это CSS. Вертикальный паддинг
при этом сохраняется: на нём держится совпадение базовых линий с подписью.

**Сделано руками в Designer** (через MCP невозможно, см. `webflow-mcp.md`): режим ссылки «текущий
элемент коллекции» и фильтр списка редакций по типу документа текущей записи.

Для баннерного списка то же самое сделано отдельно — **настройки живут на элементе, а не на
странице**, поэтому новый Collection List и новая ссылка не наследуют то, что настроено у селектора.
Проверено по факту: с `/legal-documents/cookies-2024-10-15` ссылка ведёт на `/legal-documents/cookies`.

**Тестовые данные:** запись `cookies-2024-10-15` (`6ab2c3e1e2a56ee92446513d`) заведена только чтобы
посмотреть, как расходятся страницы архива и актуальной редакции. Тело у неё то же, что у действующей.
**Удалить на катовере** (шаг 6).

## Схема коллекции `Legal documents`

| Поле | Тип | Назначение |
|---|---|---|
| `Name` | — | «Terms and Conditions» |
| `Slug` | — | `terms` у актуальной, `terms-2024-10-15` у архивной (ISO-дата: сортируется как текст, не зависит от локали) |

## Статусы редакций и запись-указатель (решено 23.09.2026)

Вводная от юристов 23.09.2026: 27 сентября вступают в силу обновлённые Terms, Privacy, Cookie
и DPA (Referral Program T&C не меняется). Клиентов уведомляют рассылкой, и между уведомлением
и вступлением в силу страницы должны **показывать действующую редакцию, но давать прочитать
будущую**. Прежняя схема «действующая по недатированному слагу, архивы по датированным» этого
не выдерживает: будущей редакции в ней нет места.

### Запись-указатель

Недатированная запись (`terms`) перестаёт быть носителем текста и становится **стабильным
адресом**: своего тела у неё нет, тело она рендерит из списка, отфильтрованного «этот же документ
+ статус *в силе*», лимит 1. Снаружи это обычная страница с полным текстом — ссылки в футере,
в письмах, в приложении и в подписанных договорах указывают на `/legal/terms` и не меняются никогда.

Почему так, а не «копировать тело в недатированную запись при смене редакции»:

- переключение статуса — единственное действие, и его делает юрист сам, без Designer и без агента;
- 62 КБ юридического текста никто не переносит руками — второй копии вообще не возникает;
- у каждой редакции постоянный датированный адрес **с рождения и навсегда**: ссылка из рассылки
  не протухает, и именно её можно вписать в договор и в запись о согласии.

Цена: в шаблоне появляется второй блок «дата + тело» под условием (на указателе — из списка,
на датированной странице — своё). Собирается один раз, дальше следить, чтобы два блока не разъехались.

Отвергнутый вариант — менять слаги местами при смене редакции. Тогда датированный адрес действующей
редакции живёт только пока она **не** в силе, между этими периодами нужен 301, который потом надо
не забыть снять. Забыли — архивный адрес молча отдаёт более новый текст. Для юр-документа недопустимо.

### Поле `Status`

`Is archived` (Switch) заменяется на `Status` (Option) с четырьмя взаимоисключающими значениями.
Именно одним полем, а не парой свитчей: два свитча можно случайно включить разом и получить
две «действующие» редакции одного документа.

| Значение | Пример слага | Где видно |
|---|---|---|
| `pointer` | `terms` | стабильный адрес, индексируется, тело из действующей редакции |
| `upcoming` | `terms-2026-09-27` | только по прямой ссылке, `noindex`, **в селекторе нет** |
| `in-force` | `terms-2024-10-15` | `noindex`, верхняя строка селектора |
| `archived` | `terms-2023-…` | `noindex`, селектор и блок «Previous versions» |

**Индексируются только пять стабильных адресов**, все датированные страницы `noindex` независимо
от статуса. Тогда не встаёт вопрос о дубликате между `/legal/terms` и датированным адресом
действующей редакции, пока они показывают один текст.

### Как отмечается действующая редакция

**Никак — она просто первая в списке.** Селектор сортируется по дате вниз и не показывает
`upcoming`, поэтому верхняя строка **всегда** действующая: это свойство сортировки, а не
соглашение, о котором надо догадываться. Ярлык дропдауна показывает ту же дату, что и верхняя
строка, — подтверждение приходит дважды без единого нового знака.

Решение от 22.09.2026 «точки в селекторе нет» этим сохраняется. Промежуточный вариант — вернуть
точку со смыслом «что сейчас в силе», раз на стабильном адресе «где я» и «что в силе» расходятся —
отклонён: дешевле убрать вопрос, чем добавить признак.

**Будущая редакция в селекторе не показывается.** Причина не в аккуратности списка: голая дата
в выпадающем списке не несёт контекста, и человек решит, что эти условия уже на него
распространяются. О будущей редакции сообщает плашка — в ней есть и дата, и слова «takes effect»,
и она заметнее строки в дропдауне, так что находимость не страдает.

Следствие: **на странице `upcoming` селектора нет вовсе** — её самой в списке нет, иначе вышел бы
ярлык с датой, которой в выпадающем списке не существует. Дата там становится обычным текстом без
стрелки — тот же режим, что уже собран для документа с единственной редакцией.

### Плашки

Все три собираются одним приёмом — **весь блок лежит внутри отфильтрованного Collection List**,
и когда подходящей записи нет, разметки нет вообще (тот же механизм, что у баннера архива):

| Где | Условие | Текст |
|---|---|---|
| стабильный адрес и действующая редакция | список: этот документ + `upcoming`, лимит 1 | «Updated terms take effect on September 27, 2026 — read them now» |
| страница `upcoming` | статус записи = `upcoming` | «This version takes effect on September 27, 2026» + ссылка на действующую |
| страница `archived` | статус записи = `archived` | «You're viewing an archived document. See the current version →» |

Плашка про будущую редакцию исчезает **сама** в момент смены статуса — отдельного шага «убрать
плашку» в процессе нет.

**Блока «Previous versions» внизу страницы не будет** (решено 23.09.2026). Он был во вводных
юристов, но те писались до того, как появился селектор редакций, а селектор закрывает то же
требование: в нём тот же список дат, теми же настоящими ссылками в разметке. Держать на одной
странице два одинаковых списка незачем.

Довод «аудитору удобнее список внизу» не выдержал проверки: аудитор ищет историю целенаправленно
и откроет дропдаун. Единственное, что терялось — находимость для того, кто историю **не** искал:
подпись «Effective date: June 8, 2026 ⌄» не объявляет себя как список версий. Это сочли
недостаточным основанием.

Автору вводных об этом надо сказать отдельно, чтобы пункт не выглядел потерянным: историю не
выбросили, она переехала в шапку, ближе к дате, которую человек и так читает.

Когда редакций станет с десяток, дропдаун перестанет быть годным контейнером — вот тогда блок
внизу и появится. Заранее не делаем.

## Выпуск новой редакции (целевой процесс)

Без Designer — может делать юрист сам:

1. **Заранее.** Завести запись `<doc>-<ГГГГ-ММ-ДД>` с новым телом, `Status: upcoming`, дата
   вступления в силу. Опубликовать. Адрес сразу рабочий — его и дают в рассылку. На стабильных
   адресах сама собой появляется плашка.
2. **В день вступления в силу.** У новой записи `Status: upcoming → in-force`, у прежней
   действующей `in-force → archived`. Опубликовать.

Стабильный адрес начинает отдавать новый текст, плашка исчезает, прежняя редакция уходит в селектор
и в «Previous versions». Ни один адрес не меняется, редиректы не нужны.

## Effective date наружу

Вопрос из вводных: можно ли вытащить дату программно — фронт передаёт её вместе с согласием
пользователя при регистрации.

Да. `effective-date` — настоящее поле CMS (DateTime), а не текст внутри тела. API отдаёт ровную
полночь UTC (`2024-10-15T00:00:00.000Z`), так что сдвига на сутки по таймзонам не будет.

Читать напрямую из браузера нельзя — Data API требует токен, а токену не место во фронте. Схема:
бэкенд ходит в Data API и кэширует.

**В запись о согласии класть не только дату, а слаг конкретной редакции** (`terms-2026-09-27`).
Тогда на вопрос «с чем именно согласился этот клиент» отвечает постоянная ссылка на замороженный
текст, а не реконструкция по дате. Вся схема датированных адресов ровно под это и строится.

который на виду.** Ссылка на `opt-out` из футера при этом трогать не нужно — привязка по `pageId`

публикации шли только на стейджинг: `publishToWebflowSubdomain: true` с пустым `customDomains`.

  посимвольно — 23 004 знака, то же число, что дала сверка при переносе 22.09.

Свежеопубликованная CMS-запись отвечает **не сразу**: `/legal/cookies-2024-10-15` отдавал 404
через несколько секунд после публикации и 200 через минуту. Проверять адреса сразу после
публикации и делать вывод по первому ответу нельзя.

### После катовера — проверить

- Пять адресов `/legal/<slug>` открываются и отдают тот же текст, что до переноса.
- `/legal/opt-out` редиректит на `/opt-out`.
- Табы в шапке ведут на CMS-страницы, а не на 404, и подсветка активного таба (`w--current`)
  по-прежнему срабатывает — она сравнивает адрес ссылки с адресом страницы, литералу это не мешает.
- У действующих редакций в head **нет** `robots`, у архивных есть `noindex, follow`.
- Селектор у документа с одной редакцией — обычный текст без стрелки.

### 6. Перевод на статусы — сразу после катовера

Катовер переносит `/legal/*` на CMS в нынешнем виде (недатированная запись = сам документ).
Схема со статусами накладывается следующим шагом:

| # | Шаг | Кто |
|---|---|---|
| 1 | Завести поле `Status` (Option, 4 значения), удалить `Is archived` | агент (API) |
| 2 | Из каждой из пяти записей сделать датированный дубль `<doc>-<дата>` со статусом `in-force`, исходную перевести в `pointer` и очистить у неё тело | агент (API) |
| 3 | Шаблон: второй блок «дата + тело» под условием, плашка про будущую редакцию, блок «Previous versions», селектор прячется на `upcoming` | агент (MCP) |
| 4 | Фильтры списков и условная видимость по `Status` | **человек**, Designer |
| 5 | Проверка на стейджинге на паре `terms` / `terms-<дата>` | агент |

### Правки после первого просмотра (23.09.2026)

**Плашка архива сидела несимметрично** — 16px сверху, 24px снизу при ровном паддинге 16.
Причина не в паддинге: у `.legal-archive-note` стоит `flex-direction: column` и
`grid-row-gap: 0.5rem`, а вторым флекс-элементом в ней лежит **embed со скриптом `noindex`**.
Он нулевой высоты и невидим, но промежуток перед ним браузер всё равно откладывает. Лечится
обнулением `grid-row-gap` — видимый ребёнок в плашке один, промежутку не между чем стоять.

Общее правило: **невидимый элемент остаётся флекс-элементом.** Скрипт, пустой div, embed без
вывода — всё это участвует в раскладке и получает свою долю `gap`. Если в контейнере с `gap`
лежит служебный элемент, симметрия ломается ровно на величину промежутка, и снаружи это читается
как неверный паддинг.

**Таб не подсвечивался на датированных редакциях.** Webflow ставит `w--current` только при
точном совпадении адреса ссылки с адресом страницы, поэтому на `/legal/cookies-2024-10-15`
не горел ни один таб и ряд выглядел сломанным. Нативного способа подсветить «по группе» нет.
Решено скриптом в подвале шаблона, каноника — [`webflow/legal-template.footer.html`](../webflow/legal-template.footer.html):
таб считается текущим, если путь равен его `href` или начинается с `href + "-"`.

Префикс берётся из самого `href`, не прописывается списком — переименование слага документа
ничего здесь не ломает. Разделитель именно `-`: совпадение по голому префиксу подсвечивало бы
и соседа, чей слаг начинается с тех же букв.

Переиспользовать сайтовый механизм `data-match-prefix` не вышло: обработчик живёт **внутри
компонента навигации** и смотрит только на свои ссылки; ни в `<head>`, ни в подвале сайта его нет.

Скрипт обязан идти через `Webflow.push`, а не по `DOMContentLoaded`: модуль ссылок Webflow на
`ready` снимает `w--current` со всех ссылок, чей адрес не совпал точно, и стирает чужую отметку.
Первая версия из-за этого выглядела неработающей, хотя тот же код из консоли отрабатывал. Разбор —
в `webflow-mcp.md`.

### Плашка стала общей: архив + будущая редакция (23.09.2026)

Классы переименованы из `legal-archive-*` в нейтральные `legal-note-*`: одна и та же плашка
обслуживает оба случая, поэтому «archive» в имени стало неверным. Внутри неё два текста под
условиями и **один общий список** со ссылкой на действующую редакцию — он одинаково нужен обоим.

```
.legal-note                      ← видна, когда Status ≠ In force И ≠ Stable address
  .legal-note-line
    p.legal-note-txt             «You're viewing an archived document.»   ← Status = Archived
    .legal-note-upcoming         ← Status = Upcoming
      p.legal-note-txt           «This version takes effect on»
      div.legal-note-date        ← привязан к полю Effective date
      p.legal-note-txt           «.»
    CollectionList → a           «See the current version →»
```

Почему одна плашка, а не две: список со ссылкой настраивается только руками в Designer
(фильтр по текущей записи), и две плашки означали бы два таких списка. Условие «показать, когда
Status ни то, ни это» выражается двумя правилами через И — отрицание в условиях Webflow есть,
дизъюнкции нет, поэтому условие сформулировано через два «не».

**Дата подставляется автоматически** — элемент привязан к полю `Effective date` записи, а не
набирается текстом. Руками дату никто не вписывает, разойтись с полем она не может.

Точка вынесена отдельным элементом, потому что у строки `gap: 0.25em`: будь точка частью общего
потока с промежутками, она отъехала бы от даты. У `.legal-note-upcoming` поэтому `gap: 0`, а
отступ перед датой задан её собственным `margin-left: 0.25em`.

**Условная видимость по Option-полю через API не ставится.** Проверено напрямую: `set_visibility`
с привязкой к `Status` отвечает `Incompatible binding: CMS field cannot bind to target`. Свитч
привязывается, Option — нет. Значит условия по `Status` — операция Designer, как и фильтры списков.

### Что настроить в Designer (23.09.2026)

| Элемент в Navigator | Что задать |
|---|---|
| `Note (archived + upcoming)` | видимость: Status ≠ `In force` И Status ≠ `Stable address` |
| `Note — ARCHIVED text` | видимость: Status = `Archived` |
| `Note — UPCOMING text` | видимость: Status = `Upcoming` |
| `Effective date + version selector` | видимость: Status ≠ `Upcoming` |
| `List — link to version IN FORCE` | фильтр: тип документа = текущий **и Status = `In force`** |
| Список редакций в селекторе | фильтр: добавить Status ≠ `Upcoming` |

**Условия поставлены и проверены 23.09.2026.** В UI Webflow условие `is not any` принимает
**список** значений, поэтому VIS-1 умещается в одно правило, а не в два через AND, как
предполагалось выше.

Проверка трёх состояний на стейджинге (`/legal/cookies`, `cookies-2024-10-15`, `cookies-2026-09-27`):

| | действующая | архивная | будущая |
|---|---|---|---|
| плашка | нет | «archived» | «takes effect on 27 September 2026» |
| ссылка из плашки | — | `/legal/cookies` | `/legal/cookies` |
| блок даты и селектор | есть | есть | **нет** |
| варианты в селекторе | 8 июня, 15 октября | те же | — |
| `noindex` | нет | есть | есть |
| подсветка таба | есть | есть | есть |

27 сентября из селектора действующей редакции исчезло, ссылка из архивной плашки ведёт на
действующую, а не на будущую. Дата в плашке подставилась из поля в том же формате, что в селекторе;
точка стоит вплотную (замер: промежуток между датой и точкой 0px, перед датой 3,5px = 0,25em).

**Незакрытый случай.** Скрипт `noindex` лежит внутри плашки, а плашка не показывается на
действующей редакции. Пока действующие редакции живут по недатированным адресам, это верно. Но
в модели с записью-указателем появится **датированная** редакция со статусом `In force` — у неё
плашки не будет, а значит не будет и `noindex`, хотя правило гласит «индексируются только пять
стабильных адресов». Решить при переходе на указатели; пометка оставлена прямо в коде embed'а.

**Строка про `FILTER-1` — это баг, который вносит появление будущей редакции.** Список ссылки «See the
current version» сейчас настроен как «сортировка по дате вниз, лимит 1», то есть «самая свежая».
Пока будущих редакций не было, самая свежая и была действующей. Теперь самая свежая — это
редакция от 27 сентября, которая ещё не вступила в силу, и архивная плашка повела бы на неё.
Признак «действует» должен быть явным, а не выводиться из даты.

Класс `.legal-rt` почти пустой — в нём только `max-width: 800px` и правило для `h3`. Всё остальное
падает на **глобальные тег-стили**, и оттуда приезжает:

- **интерлиньяж 1,2 на теле** — для документа в 30 000 знаков это нечитаемо тесно;
- **вес 600 на всём теле** — полужирный от первой буквы до последней, акцент перестаёт работать;
- **`h6` (12px) мельче тела (15,84px)** — иерархия перевёрнута, а в Privacy таких заголовков 19;
- **строка ~100 знаков** (800px при 15,84px) при комфортных 60–75.

Донор значений — **`.birchcourse-rich-text`** (курс, `/birch-course/*`, есть свой styleguide:
`/styleguides/birch-course-styleguide`). Это самый полно прописанный рич-текст-класс на сайте:
правило на каждый тег, нормальная убывающая лесенка `h2 → h3 → h4 → h5 → h6`, оверрайды на
991 / 767 / 479, и в нём уже стоит `h4 { max-width: none }` — глобальная грабля в 400px обезврежена.

| `h2` | 1,4rem / 1,0, ls −0,02em, m 1,875rem / 0,75rem | нет |

Кегль тела у курса и у юр-страниц **одинаковый** (0,9rem). Разница только в интерлиньяже и весе:
юр-страницы это «курс со сломанной настройкой».

Кейсы (`.cs-rich`) как донор хуже: класс прописан беднее, и он заточен под короткие абзацы кейса.
Блог (22px) — настройка «читать подряд», а юр-документ сканируют.

**Решение (22.09.2026): база + комбо, один общий класс на оба раздела.**

- `.birchcourse-rich-text` переименовывается в нейтральное `rich-text-base`; все правила по тегам
  остаются в нём — единственный источник правды для интерлиньяжа, весов и лесенки заголовков.
- Курс — `rich-text-base rt-course`, юр-документы — `rich-text-base rt-legal`.
- В комбо только расхождения. У `rt-legal` это `max-width: 680px`, и пока всё.

Проверено перед решением: `birchcourse-rich-text`, `legal-rt` и `centered-terms` не упоминаются
ни в одном инлайновом `<style>` или скрипте ни на одной из проверенных страниц (курс, styleguide,
блог, юр-страница) — значит на них не завязан ни страничный, ни сайтовый кастом-код, и
переименование безопасно. Прецедент комбо в этом классе уже есть: `.birchcourse-rich-text.mob`.

Переименование класса — операция Designer; в MCP rename не найден (уточнить при сборке шаблона).

**Колонка сужается с 800 до 680px.** У курса абзацы короткие, а у DPA тело 62 КБ; при 800px строка
выходит ~105 знаков при комфортных 70–80.

Писать стили **тег-стилями внутри класса** (`.legal-rt h5`), как сделано у `.cs-rich`: через
`data_style_tool` с `style_name: "h5"` + `parent_style_names: ["legal rt"]` (имя родителя как в
Designer, с пробелом). Подробности — `docs/webflow-mcp.md`.
