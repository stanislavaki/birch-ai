# Версионирование юридических документов (`/legal/*`)

План переноса юр-документов из статичных страниц в CMS-коллекцию, чтобы у каждого документа
была история редакций: актуальная всегда по адресу без даты, прошлые — по адресу с датой,
переключение через селектор на строке `Effective date`.

Статус на 22.09.2026: **коллекции заведены, идёт заливка документов.** Шаблон не собран,
катовер не начинался.

| Сущность | Id |
|---|---|
| Коллекция `Legal document types` | `6ab28b9c59aafa375acd46ac` |
| Коллекция `Legal documents` | `6ab28b9f2caaa5ecf2d28799` |
| Тип Terms / Privacy / Cookies / Affiliate / DPA | `…d235` / `…d237` / `…d239` / `…d23b` / `…d23d` (префикс `6ab28d53ca76ba500094`) |

Слаги коллекций временные (`legal-documents`, `legal-document-types`) — постоянный `legal`
отдаётся только на катовере, см. «Порядок работ». Записи держим черновиками (`isDraft: true`),
пока не собран шаблон: иначе ближайшая полная публикация кем угодно из команды выложит
дубли юр-документов по адресам `/legal-documents/*`.

## Как устроено сейчас

Шесть статичных страниц в папке `legal` (`6716718ea408f53194adfac2`), сайт `6716718ea408f53194adf9a9`:

| Страница | `page_id` | URL | Effective date | Тело |
|---|---|---|---|---|
| Terms and Conditions | `6716718ea408f53194adfafe` | `/legal/terms` | October 15, 2024 | rich text 24 КБ |
| Privacy Policy | `6716718ea408f53194adfae2` | `/legal/privacy` | June 8, 2026 | rich text 32 КБ |
| Cookie Policy | `6716718ea408f53194adfa58` | `/legal/cookies` | June 8, 2026 | rich text 7 КБ + таблица |
| Data Processing | `68d6608f5f68aa2c38c2d290` | `/legal/data-processing` | June 8, 2026 | rich text 58 КБ + таблица |
| Referral Program T&C | `6716718ea408f53194adfae4` | `/legal/referral-program-terms-and-conditions` | October 15, 2024 | rich text 7,6 КБ |
| Opt Out | `6a392964f7734eba5c2e8613` | `/legal/opt-out` | — | **не документ этого семейства** |

Структура тела одинаковая у всех пяти документов:

```
.centered-terms (max-width 800px, центрируется)
  .legal-menu-tabs > .tabs-cont > a.legal-menu-link.tab2   ← табы между документами
  p._14px.grey                                             ← «Effective date: …» ← сюда селектор
  .legal-rt.w-richtext                                     ← тело
  [.w-embed > .cookie-table-wrap > table]                  ← таблицы: отдельный HTML embed
  [.legal-rt.w-richtext]                                   ← продолжение тела после таблицы
```

`Opt Out` — лендинг с формой и canvas-анимацией, без даты и вне табов. В систему не входит.

### Что проверено по содержимому (важно для переноса)

- **Теги внутри rich text:** только `p`, `h3`, `h5`, `h6`, `ul`/`li`, `a`, `strong`, `em`, `br`.
  Всё это родное для CMS rich text — тела переезжают без разбора и пересборки.
- **Ни одного `id`-якоря и ни одной ссылки на `#раздел`** ни в одном документе. Это была главная
  опасность переезда (rich text не даёт ставить `id` на заголовки) — её нет.
- **Таблицы уже лежат в HTML embed**, а не в rich text. В CMS embed вставляется внутрь
  rich-text-поля (плюсик на новой строке в CMS-редакторе → HTML embed), то есть переезжает один-в-один.
  Формулировка «CMS rich text не умеет таблицы» неверна: нет *элемента* «таблица», но embed внутри поля есть.
- **Размеры:** максимум — DPA, 62 КБ после сборки тела. Лимит текстового поля Webflow порядка
  мегабайта, запас кратный.
- **Таблица проходит через Data API без изменений** (проверено 22.09.2026 на Cookie Policy):
  отправленный `<div class="w-embed"><table class="cookie-table">…` вернулся байт в байт, ничего
  не вырезано и не экранировано. Как это выглядит в CMS-редакторе и на опубликованной странице —
  проверить на стейджинге.
- **Заливка упирается в канал.** Тела идут через tool-вызовы, то есть агент набирает 62 КБ
  юридического текста руками — риск тихо потерять оговорку. Правильный путь: API-токен Webflow
  в локальном файле и `curl` прямо из скачанных HTML. Запасной — заливка через MCP с обратной
  выкачкой и построчной сверкой скриптом.

## Решения (согласовано 22.09.2026)

- **Полный CMS.** Одна коллекция, и текущие, и архивные редакции — записи в ней. Причина: статичные
  архивы замораживают не только текст, но и обвязку (табы, селектор, типографика). Через три года это
  ~20 страниц, и любая правка стиля — двадцать раз руками.
- **Архив копится с сегодняшнего дня.** Текстов прошлых редакций нет, на старте по одной записи на
  документ, все `Is current`.
- **Архивы индексируются.** Никакого `noindex`, от путаницы защищает баннер на архивной странице.
  Это снимает единственный кусок, который в CMS не решался нативно (индексация настраивается
  на шаблоне, то есть общая для всех записей).
- **Селектор показывает все редакции**, текущая с пометкой.
- **Полей `summary of changes` и страницы-хаба нет.** Хаб (список всех редакций всех документов)
  нужен только под комплаенс-сценарий — аудитор просит историю изменений. Заводится за полчаса
  поверх той же коллекции, когда попросят.
- **`/legal/opt-out` → `/opt-out`** с 301, если префикс `legal` иначе не отдаётся коллекции.

## Схема коллекции `Legal documents`

| Поле | Тип | Назначение |
|---|---|---|
| `Name` | — | «Terms and Conditions» |
| `Slug` | — | `terms` у актуальной, `terms-2024-10-15` у архивной (ISO-дата: сортируется как текст, не зависит от локали) |
| `Document type` | Reference → `Legal document types` | группирует редакции одного документа; та же коллекция кормит табы |
| `Effective date` | DateTime | дата в шапке и в селекторе |
| `Is current` | Switch | помечает действующую редакцию |
| `Superseded date` | DateTime | для баннера «действовала с … по …»; пусто у актуальной |
| `Body` | RichText | тело, включая embed с таблицей |
| meta title / description / OG | — | сейчас забиты руками на каждой странице |

Вторая коллекция `Legal document types` — 5 записей (Terms, Privacy, Cookies, Affiliate, DPA),
нужна для reference-фильтра селектора и заодно кормит ряд табов, который сейчас статичный.

## Выпуск новой редакции (целевой процесс)

Три шага, без Designer — может делать юрист сам:

1. Дублировать запись → у дубликата слаг `terms-2024-10-15`, `Is current` off, `Superseded date` =
   дата новой редакции. Архив готов, тело уже внутри.
2. В исходной записи (слаг `terms`) заменить тело и поднять `Effective date`.
3. Опубликовать.

Адрес действующего документа при этом **никогда не меняется** — ссылки из приложения, писем и
подписанных договоров не ломаются, редиректы не нужны.

## Что проверить до старта

1. **Префикс `legal` для коллекции.** Чтобы `/legal/terms` остался тем же адресом, коллекции нужен
   слаг `legal`, а папка `legal` с тем же именем существует. Скорее всего Webflow не даст, пока
   папка на месте. Порядок безопасной проверки — ниже, в «Порядке работ».
2. **Фильтр селектора по текущей записи.** Шаблон один на все документы, значит Collection List
   должен фильтроваться «редакции того же документа, что и открытая запись» — стандартный паттерн
   «похожие статьи» через reference-поле. В Designer он есть; **через MCP словарь фильтров
   (`{fieldSlug, operator, value}`) принимает только литеральные значения**, то есть настраивать
   фильтр, возможно, придётся руками в Designer. Фолбэк, если нативно не выйдет: рендерить все
   редакции и фильтровать по `data`-атрибуту скриптом.

## Порядок работ

1. Создать `Legal document types` (5 записей) и `Legal documents` **с временным слагом**
   (`legal-documents`), не `legal`. Временный потому, что новая коллекция создаёт шаблон-страницу,
   которая уедет на прод при ближайшей полной публикации кем угодно из команды: коллизия с живой
   папкой `legal` в этот момент недопустима.
2. Залить пять документов в коллекцию через API (тела как есть, таблицы embed'ами внутрь поля).
3. Собрать шаблон: табы, селектор редакций, баннер архивной редакции, типографика (ниже).
4. Проверить на стейджинге по адресам `/legal-documents/*`, сверить рендер со старыми страницами.
5. **Катовер одной сессией:** `opt-out` выносится из папки (`parentFolderId: null`, слаг `opt-out`)
   → удаляются пять статичных страниц и папка `legal` → слаг коллекции меняется на `legal` →
   добавляется 301 `/legal/opt-out` → `/opt-out` → одна публикация. Даунтайма нет, адреса
   документов сохраняются.

Удаление страниц и папки, смена слага коллекции и редиректы — через Designer/Site settings:
в MCP нет ни `delete_page`, ни `update_collection`, ни управления редиректами.

## Типографика тела

**Сейчас у юр-страниц она сломана** — замеры на 1440px, `html { font-size: 17.6px }`:

| | колонка | `p` | line-height | вес `p` | заголовки |
|---|---|---|---|---|---|
| `.legal-rt` (юр.) | 800px | 15,84px | 19,0 (**1,2**) | **600** | h3 30/39, h5 19,8, **h6 12px** |
| `.cs-rich` (кейсы) | 763px | 17,6px | 26,4 (1,5) | 600 | h2 41,8, h3 26,4 |
| `.blogpost-rich-text` (блог) | — | 22px | 30,8 (1,4) | 500 | h2 44, h3 28,8 |

Класс `.legal-rt` почти пустой — в нём только `max-width: 800px` и правило для `h3`. Всё остальное
падает на **глобальные тег-стили**, и оттуда приезжает:

- **интерлиньяж 1,2 на теле** — для документа в 30 000 знаков это нечитаемо тесно;
- **вес 600 на всём теле** — полужирный от первой буквы до последней, акцент перестаёт работать;
- **`h6` (12px) мельче тела (15,84px)** — иерархия перевёрнута, а в Privacy таких заголовков 19;
- **строка ~100 знаков** (800px при 15,84px) при комфортных 60–75.

Донор значений — **`.birchcourse-rich-text`** (курс, `/birch-course/*`, есть свой styleguide:
`/styleguides/birch-course-styleguide`). Это самый полно прописанный рич-текст-класс на сайте:
правило на каждый тег, нормальная убывающая лесенка `h2 → h3 → h4 → h5 → h6`, оверрайды на
991 / 767 / 479, и в нём уже стоит `h4 { max-width: none }` — глобальная грабля в 400px обезврежена.

| | `.birchcourse-rich-text` | `.legal-rt` |
|---|---|---|
| `p` | 0,9rem / **1,4em**, вес 500, `wght 540`, mb 0,75rem | 0,9rem / **1,2**, вес **600** |
| `h2` | 1,4rem / 1,0, ls −0,02em, m 1,875rem / 0,75rem | нет |
| `h3` | 1,2em / 1,3, ls −0,02em, `max-width: none` | 30px / 1,3 |
| `h4` | 1em / 1,3, `max-width: none` | нет |
| `h5` | 0,9em / 1,5 | нет |
| `h6` | 0,833em / 1,4 | нет |
| `ul` / `ol` / `li` | padding-left 25/32px, li 1,4, mb 0,375rem | нет |
| `blockquote` | плашка light-gray, радиус 0,5em, 22px | нет |

Кегль тела у курса и у юр-страниц **одинаковый** (0,9rem). Разница только в интерлиньяже и весе:
юр-страницы это «курс со сломанной настройкой».

Кейсы (`.cs-rich`) как донор хуже: класс прописан беднее, и он заточен под короткие абзацы кейса.
Блог (22px) — настройка «читать подряд», а юр-документ сканируют.

**Решение (22.09.2026): база + комбо, один общий класс на оба раздела.**

- `.birchcourse-rich-text` переименовывается в нейтральное `rich-text-base`; все правила по тегам
  остаются в нём — единственный источник правды для интерлиньяжа, весов и лесенки заголовков.
- Курс — `rich-text-base rt-course`, юр-документы — `rich-text-base rt-legal`.
- В комбо только расхождения. У `rt-legal` это `max-width: 680px`, и пока всё.

Проверено перед решением: `birchcourse-rich-text`, `legal-rt` и `centered-terms` не упоминаются
ни в одном инлайновом `<style>` или скрипте ни на одной из проверенных страниц (курс, styleguide,
блог, юр-страница) — значит на них не завязан ни страничный, ни сайтовый кастом-код, и
переименование безопасно. Прецедент комбо в этом классе уже есть: `.birchcourse-rich-text.mob`.

Переименование класса — операция Designer; в MCP rename не найден (уточнить при сборке шаблона).

**Колонка сужается с 800 до 680px.** У курса абзацы короткие, а у DPA тело 62 КБ; при 800px строка
выходит ~105 знаков при комфортных 70–80.

Писать стили **тег-стилями внутри класса** (`.legal-rt h5`), как сделано у `.cs-rich`: через
`data_style_tool` с `style_name: "h5"` + `parent_style_names: ["legal rt"]` (имя родителя как в
Designer, с пробелом). Подробности — `docs/webflow-mcp.md`.
