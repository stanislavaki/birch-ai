# Webflow MCP — нативная сборка блоков

Раздел про прямую сборку блоков в Webflow через Webflow MCP (не embed, не dev-страница). Перед любыми тулами один раз вызвать `webflow_guide_tool`. `site_id` не угадывать — брать из `list_sites` (текущий: bir.ch = `6716718ea408f53194adf9a9`). Designer-тулы требуют, чтобы вкладка Webflow Designer была открыта и на переднем плане; data-тулы (builder/style) работают headless по `pageId`.

### Возможности тулинга (что можно и что нельзя через API)

- **Можно через API:** создавать элементы (`data_element_builder`, в т.ч. вложенные деревья через `children[]`), создавать/править стили и combo-классы (`data_style_tool`), ставить иконку сразу при создании (`type: "Image"` + `set_image_asset`), загружать ассеты (`asset_tool`), снимать снапшоты элементов (`element_snapshot_tool`).
- **`data_element_tool` есть** (появился позже, старая заметка о его отсутствии не актуальна): `query_elements` / `get_all_elements` читают дерево страницы, `move_element` и `remove_element` двигают и удаляют, плюс `set_text` / `set_style` / `set_heading_level` / `set_attributes`. Дерево читать через `query_elements` с `element_id` + `children_depth: -1` — id всех потомков приходят разом.
- **`query_elements` врёт про ссылку у Link Block — `link.linkType: "none"` даже когда ссылка стоит** (подтверждено 08.2026: у обоих `card-link` API упорно показывал `none`, а на опубликованной странице `<a href="/ai">`/`<a href="/mcp">` — ссылки были). Не диагностировать наличие ссылки по `settings.link` из `query_elements` — это поле ненадёжно (возможно, читает только `set_link`-заданные значения, а не проставленные в Designer). Проверять ссылку **по факту**: `curl` опубликованной страницы + `grep '<a ... class="<class>"'`, либо `get_attributes` с `name:"href"`. Мораль шире: прежде чем говорить пользователю «ссылки нет», сверить с реальным рендером — доверие к одному полю MCP-ответа дороже трёх ложных «у тебя не сохранилось».
- **`data_scripts_tool` есть и читает/пишет кастом-код страницы** (старая заметка «недоступен» не актуальна, подтверждено 08.2026): `get_page_freeform_code` **читает** freeform head/footer страницы (то, что в Page Settings → Inside `<head>` и Before `</body>`), `set_page_freeform_code` **перезаписывает** блок целиком (`location: "head"` | `"footer"`, `content` — полный сырой код с тегами `<style>`/`<script>`). Плюс site-level (`get/set_site_freeform_code`) и реестр скриптов (`register_inline_script`/`add_page_script`/…). **Копипаст кастом-кода пользователем больше не нужен** — читаю блок сам, вношу правки, пишу обратно; порядок: сначала `get_page_freeform_code`, потом `set_…` полной новой версией (не «добавить кусок», т.к. запись заменяет весь блок). Лимит символов есть у инлайн-скриптов реестра (2000) и у site-level; page freeform head/footer — это поля Page Settings. Всё равно только ASCII (см. правило про UTF-8 выше).
- **Нельзя через API (только руками в Designer):** **дублировать элемент** (нет никакого `duplicate`; билдер умеет только собирать из схемы заново).

- **`data_component_tool` и `data_component_props_tool` есть** (MCP 2.0.1, проверено 01.09.2026 — старая заметка «нет `data_component_tool`, компоненты только руками» **не актуальна**, как и в своё время заметка про `data_element_tool`). Через API можно: `create_blank_component`, `transform_element_to_component` (самый удобный путь: собрать элемент билдером → превратить в компонент, `replace: true` сразу подменяет элемент инстансом), `insert_component_instance`, `unregister_component`, а также заводить пропы (`create_prop`: `textContent`, `string`, `richText`, `image`, `link`, `video`, `number`, `boolean`, `id`, `altText`) и проставлять их значения у инстансов (`set_component_instance_prop_values`). То есть «компонент с пропами + авто-заполнение мной» больше не взаимоисключающи.
- **`before`/`after` в билдере нельзя якорить на инстанс компонента** — `data_element_builder` с `creation_position: "before"` и `parent_element_id` = id инстанса падает с `Cannot insert elements directly into a component instance`: API трактует переданный id как родителя, а не как соседа, даже для before/after. Обходной путь — брать реального родителя и позицию: чтобы встать над первым потомком, `prepend` в родителя. Реальный кейс: баннер над меню — `prepend` в `page-wrapper`, потому что `super-navigation-component` там первый ребёнок.

- **Код HTML-эмбеда пропом не пробросить: у `code` `canBind: false`** (проверено на `HtmlEmbed` 01.09.2026 через `get_settings` → `query_settings`). У эмбеда всего три сеттинга: `domId` (`canBind: true`), `visibility` (`canBind: true`), `code` (`canBind: false`). Практический вывод для кампанийных блоков: компонент, оборачивающий эмбед, **не может** отдать копирайт редактору пропом — текст остаётся внутри кода, правится в репе и перевставляется. Зато `visibility` биндится, поэтому булев проп «показывать баннер» на инстансе сделать можно, и это самый дешёвый выключатель кампании. Если нужен именно редактируемый маркетологом текст — собирать блок нативными элементами, а не эмбедом.

- **Код в эмбед писать через `data_element_settings_tool > set_settings`, ключ `code`** (`static_text.value`). Билдерный `settings` при создании для этого не годится — он «Only applies to DOM type elements», у `HtmlEmbed` игнорируется. Порядок: создать `HtmlEmbed` → `set_settings` с кодом → `transform_element_to_component`. Код переживает трансформацию: после неё читать его надо у элемента внутри дефиниции (`element_id` = id компонента в обоих полях + `scope_component_id`).

- **Повторяющиеся блоки — дублировать в Designer, а не пересобирать билдером.** Дубль (Cmd+D) переносит классы один-в-один и не проходит через резолвинг имён (см. гочу ниже), поэтому для второй-пятой карточки ряда быстрее и надёжнее попросить пользователя сделать Cmd+D, а потом заполнить контент через `set_text`. Билдером собирать только первый экземпляр.
- **id колонок/контейнеров** брать из ответов `data_element_builder` (`return_element_info: true`), из `query_elements` или из `get_selected_element` (попросить пользователя кликнуть нужный элемент).

### Webflow-гочи (подтверждено на практике)

- `font-family` через переменную — только с префиксом: `variable_as_value: "variable-<id>"` (без префикса `create_style` падает internal error).
- **Класс назначается по имени, а имя не уникально — прилипает чужое комбо.** API резолвит строку в `style_names` в *стиль*, а комбо-класс носит имя своего хвоста: и глобальный `.paragraph-sm`, и комбо `.u-text-white.u-text-center.paragraph-sm` называются «paragraph-sm». Выбирается комбо, и элемент получает всю цепочку (в реальном кейсе к описанию приклеилось 8 классов, текст стал белым и центрованным). Правило: **через API назначать только уникальные имена классов** — свои `block__element` работают всегда. Если нужен неуникальный нативный класс, есть три пути: (1) поставить его руками в Designer — там резолвинга нет; (2) назначить и **сразу перечитать** `query_elements`, проверив `styleNames`; (3) завести свой класс на тех же нативных **переменных** (`Font Size/*`, `_sizes---*`, цветовые) — токены переиспользуются, даже если класс новый.
- **Нативные классы дизайн-системы переиспользовать, а не переписывать — но каждое назначение проверять.** Заранее предсказать, соскочит ли резолвинг, нельзя: `h3` и `paragraph-lg` встали чисто (`styleNames: ["h3"]`), а `h4` и `paragraph-sm` утащили чужие цепочки. Наличие конкурентов по имени тоже не приговор — у `h3` есть тег-стили (`.legal-rt h3`, `default-h3`), и всё равно назначился правильный глобальный класс. Поэтому рабочий цикл: **назначил → сразу `query_elements` → сверил `styleNames`**; чисто — оставляем, цепочка — откат и в Designer. Одна лишняя проверка дешевле, чем свой дубль типографики (так у нас родились ненужные `promo-card__title` / `promo-card__desc`, потом удалены). На голый тег не полагаться: `default-h3` на этом сайте — Poppins 24px с `max-width: 400px`, а не дизайн-система.
- **Переменная / комбо / утилита — что когда.** Три разных инструмента переиспользования, их легко перепутать: **вариант одного компонента** → комбо-класс (`card-base` + `card-base--yellow`); **одно значение между блоками** → переменная (оба класса ссылаются на `_sizes---2rem`, правка в одном месте); **правило из нескольких свойств или с брейкпоинтами между разными блоками** → глобальная утилита. Именно брейкпоинт решает: переменная не несёт медиа-правило, поэтому «десктоп 2rem → мобилка Padding/Card» пришлось бы дублировать в каждом карточном классе — вместо этого завели `u-card-pad` и сняли паддинги с `.tool-card`. Утилита оправдана, когда потребителей ≥3; ради двух блоков и пары статичных свойств её не заводить. Имена давать по **стилю/роли**, а не по месту: `btn-ghost`, `card-media`, `card-base` переиспользуются, `promo-explore` и `promo-card__shot` — нет.
- **Панель Inheritance длинная — это не вложенность.** Webflow перечисляет все селекторы, влияющие на элемент, от слабого к сильному: сначала `Body (All Pages)` и классы родителей, потом классы самого элемента. Верхние 2–3 строки будут у любого элемента сайта. Базовый класс, показанный дважды (`promo-card`, затем `promo-card promo-card--ai`), — это не дубль, а два селектора: сам класс и комбо-цепочка; галочка отмечает редактируемый. Полезный побочный эффект: панель показывает, откуда наследуется нежданное — так нашёлся класс `centered` на родителе, из-за которого текст в карточках центровался и потребовался явный `text-align: left`.
- **Утилитарный класс с `order` на брейкпоинте — мина замедленного действия.** `order` не действует ни на что, кроме прямых детей флекс/грид-контейнера. Поэтому правило вида `@media (max-width: 991px) { .u-mb-sm { order: 1 } }`, повешенное на **маргин-утилиту**, в блочном потоке не делает ничего и живёт незамеченным годами — а стоит положить элемент с этим классом во флекс, как он молча уезжает в конец на планшете. Диагностируется не по внешнему виду блока, а чтением всех правил класса по брейкпоинтам. Симптом: на десктопе порядок верный, на планшете элементы поменялись местами, хотя разметку никто не трогал.
  Прежде чем снимать такое правило глобально — **проверить, не держит ли оно чужую вёрстку**. Поиск кандидатов дешевле всего делать статически: скачать опубликованный CSS и страницы `curl`'ом и разобрать скриптом — найти все элементы с классом, у каждого посмотреть родителя и **позицию среди соседей** (если элемент и так последний, `order` ничего не меняет — отбрасывать сразу).
  **Но статический разбор даёт только кандидатов, не ответ.** Определять флекс-родителя по тому, что у его класса «где-то в CSS есть `display: flex`», — неверно: правило может жить в другом контексте (`.container.cc-nav`, `@media (min-width: 1920px)`), а на конкретной странице элемент вычисляется в `block`, где `order` не действует. Проверять только **вычисленным** `display` в живом браузере и сравнением DOM-порядка с визуальным (`getBoundingClientRect().top`), на каждой ширине внутри действия правила. Реальный кейс: статика дала 4 «сломанных» страницы, замер подтвердил одну — на `/features` `.ad-platform_content` реально флекс и там 8 осознанных перестановок (правило оставили, чинили точечно комбо-классом), а на `/snapchat-ads-automation` родители оказались блочными и никакого бага не было.
- **Свойство `gap` `data_style_tool` не принимает** — падает с «An internal error occurred». Флекс-гэп задавать парой `grid-row-gap` + `grid-column-gap` (Webflow хранит его так).
- **Брейкпоинт в `data_style_tool` — ключ `breakpoint_id`, и ошибка в нём молчаливая.** Значения: `main` (десктоп), `medium` (≤991), `small` (≤767), `tiny` (≤479), плюс `large`/`xl`/`xxl`. Любое другое имя ключа (напр. `breakpoint`) тул **не валидирует и не ругается** — он просто пишет свойства в базовые. То есть попытка задать мобильные значения перезаписывает десктопные, и заметить это можно только по ответу тула. Правило: после записи на брейкпоинт **читать ответ и проверять, что свойства легли в `breakpoints.<id>`, а не в `base`**. Реальный кейс: логотипы 80px стали 50px на всех ширинах.
- **Container queries в Webflow через MCP работают.** `data_style_tool` принимает и сохраняет `container-type: inline-size`, юниты `cqi`/`cqw` и функции `min()`/`clamp()` — проверено чтением стилей обратно. Это рабочий способ сделать блок «резиновым от своего контейнера», а не от вьюпорта: контейнером объявляется обёртка, внутренние размеры задаются в `cqi`. Особенно полезно, когда несколько картинок с **разными пропорциями** должны держать одинаковую высоту: задавать всем одну `height` в `cqi` + `width: auto`, а не считать каждой свой процент ширины (иначе при замене ассета проценты надо пересчитывать). На узких брейкпоинтах `cqi` подпирать потолком через `min(Ncqi, Nrem)` — иначе к верхней границе брейкпоинта размер улетает.
- **`type: "TextBlock"` в билдере создаёт обычный div**, `set_text` в него не пишется («This element doesn't support text») и остаётся плейсхолдер «This is some text inside of a div block.». Для любого текстового узла использовать `Paragraph` или `Heading` — они принимают `set_text` при создании.
- **`set_text` в `children[]` билдера — объект, не строка:** `"set_text": { "text": "..." }`. Строкой валится вся схема.
- **Кастомные CSS-свойства (`--foo`) `data_style_tool` не принимает.** Цветовые токены/варианты — через combo-классы с прямым `background-color`, не через `var()`.
- `alt` — зарезервированный атрибут; на `<img>` через `set_attributes` не ставится и роняет весь билд. Alt задавать в Designer или опускать.
- Кастомный `<img src>` Webflow превращает в свой `Image`-элемент и требует `set_image_asset` (asset id), сырой `src` игнорируется. Для иконок использовать `type: "Image"` + `set_image_asset`.
- **asset id = 24-символьный хэш в начале имени файла на CDN** (`.../<hash>_Name.svg`). Иконки/картинки, уже загруженные на сайт, ставятся сразу по этому id — повторная загрузка не нужна (`upload_image_by_url` для существующего вернёт тот же id).
- Заголовок/описание наследуют `text-align` со страницы (часто `center`) — задавать `text-align: left` явно, если нужно по левому краю.
- **`!important` в Webflow задаётся только кастомным CSS.** Ни панель стилей Designer, ни `data_style_tool` (MCP) его не сохраняют — Webflow вырезает. Любой форс-оверрайд (перебить глобальную переменную, глобальный reset, стиль компонента) делать через `<style>` в Page Settings → Inside `<head>`, а не через класс.
- **Радиус на обёртке держится только пока картинка заполняет обёртку.** Классическая связка «`border-radius` + `overflow: hidden` на блоке, картинка внутри» скругляет не картинку, а вырез блока. Пока картинка совпадает с блоком по размеру, разницы не видно. Стоит поменять её пропорцию (или блоку растянуться по `align-items: stretch` соседней колонки) — картинка «повисает» внутри и показывает собственные прямые углы, а скруглённый вырез блока оказывается на пустом месте. Симптом характерный: **скругления есть у части страниц и нет у остальных**, хотя вёрстка одна — скруглены ровно те, где высота блока случайно совпала с высотой картинки. Лечится переносом радиуса на саму картинку (тем же токеном, что у блока, через `variable_as_value` — литералом нельзя, `var(--foo)` тул не принимает), а не подгонкой высот. Диагностировать сравнением `getBoundingClientRect().height` картинки и её родителя по всем страницам разом.
- **`border-radius` и `object-fit: contain` несовместимы: радиус ложится на бокс, а не на видимую картинку.** При `contain` элемент сохраняет размер контейнера, а изображение вписывается внутрь с полями — скругляются пустые углы бокса, визуально эффекта ноль. Заметить это по коду легко, по макету — нет, потому что «правило же применилось». Универсальное решение (работает при любой пропорции, без расчётов под конкретные размеры): заставить бокс обжимать картинку — `position: absolute; inset: 0; margin: auto; width: auto; height: auto; max-width: 100%; max-height: 100%`. Это центрирует что угодно и делает бокс равным видимому изображению, поля сохраняются. Проверка — сравнить `getBoundingClientRect()`-пропорцию бокса с `naturalWidth/naturalHeight`: должны совпасть.
- **Обжатый бокс ломает анимацию, которая двигает слайды в процентах.** `translateX(100%)` считается от ширины **самого элемента**. Пока слайд был во всю рамку, это совпадало с шириной рамки; после обжатия узкий вертикальный слайд уезжает только на свою ширину и остаётся торчать в кадре. Переводить сдвиг в пиксели ширины рамки (`viewport.clientWidth`) — этого хватает всегда, потому что картинка никогда не шире рамки. Правило общее: если меняешь размер элемента с «во весь контейнер» на «по контенту», проверь весь код, где от его размеров считаются проценты.
- **Перебить часть значения, заданного переменной-токеном, — литералом на конкретном элементе, не трогая токен.** Если свойство привязано к Webflow Variable (напр. `border-radius` = токен на все 4 угла), а нужно изменить только часть (только нижние углы → `0`), задавать литеральные значения локально на элементе/углах, а не править саму переменную (иначе поедет везде). При необходимости форса — см. правило про `!important` выше.

### Ассеты и картинки в CMS (подтверждено 08.2026 на переводе кейсов в WebP)

- **Загрузка файла с диска — два шага, оба доступны по API.** `data_assets_tool` → `create_asset` (нужны `file_name` и `file_hash` = **md5 сырых байт в hex**, не sha и не base64) возвращает `uploadUrl` + `uploadDetails`. Дальше — `multipart/form-data` POST на `uploadUrl`, где каждое поле `uploadDetails` кладётся отдельным полем формы, а файл — полем `file`. Имена полей в ответе camelCase, а S3 ждёт канонические: `xAmzAlgorithm` → `X-Amz-Algorithm`, `successActionStatus` → `success_action_status`, `contentType` → `Content-Type`, `cacheControl` → `cache-control`. Успех — HTTP **201**.
- **Webflow перезаливает любую картинку, отданную по URL, — включая ссылки внутри рич-текста.** Записал в CMS-поле `{"url": …}` — в базе окажется **другой** адрес: Webflow скачивает файл и кладёт к себе, под каноническим префиксом сайта (`cdn.prod.website-files.com/671679ee69322cdc0f54b3d3/…`), с новым id в начале имени. Следствия: (1) сверять запись «до/после» по URL бессмысленно — сравнивать надо с замаскированными адресами; (2) если файл заливался напрямую через `create_asset`, он после этого продублируется — один экземпляр по адресу загрузки, второй перезалитый; лишние потом чистятся вручную. Избежать дубля можно, передавая в поле `fileId` вместо `url`, но для картинок **внутри рич-текста это не работает** — там хранится сырой HTML с `src`, и Webflow всё равно перезальёт.
- **Про размер решать ДО загрузки, а не после.** Порядок всегда один: обжать локально → залить только обжатое. Большие исходники на сайт не попадают вообще. Если картинка заведомо крупнее того, что нужно (типовой случай — OG крупнее рекомендованных 1200×630), предложить пережатие **до** первой загрузки и залить одну версию. Иначе на сайте остаётся тяжёлый файл, который ничем не используется: у нас так залёг OG на 1103 КБ, пока решение о пережатии принималось после заливки. Мелочь, но именно из таких мелочей набирается мусор в Asset manager.
- **`delete_asset` — мягкое удаление: запись уходит из Asset manager, файл на CDN остаётся и продолжает отдаваться.** То есть удаление наводит порядок в списке, но не освобождает место и не ломает вёрстку, если на файл где-то ещё ссылаются по прямому адресу. Перезалитой Webflow'ом копии отдельной записи может не быть вовсе — попытка удалить её по id вернёт 404, и это нормально, а не ошибка. Перед удалением всё равно проверять, что адрес не встречается ни на одной живой странице: восстановления через API нет.
- **После перезаливки живой — всегда перезалитый экземпляр, обновлять надо его.** Загрузка через `create_asset` + S3 и последующая запись URL в CMS-поле дают **две** записи ассета: исходную и сделанную Webflow'ом. Страницы ссылаются на вторую, первая остаётся сиротой. Практическое следствие: если заменить файл «не в той» копии, на сайте ничего не изменится — типовые полчаса отладки на ровном месте. Отличить сироту по адресу **нельзя**: сайт легально использует оба префикса (`/6716718e…/` встречается и у обычных ассетов вроде иконок платформ). Ориентироваться только на тот URL, который реально лежит в CMS-поле. Удалять сирот не нужно — они не грузятся и ничего не стоят, а удаление необратимо и требует аудита ссылок по всем страницам.
- **Ответы `list_collection_items` и `update_collection_items` на коллекции кейсов не влезают в лимит тула** (~120 КБ) — они приходят файлом на диск. Это **не ошибка**: вызов прошёл, просто результат сохранён. Разбирать сохранённый файл скриптом, а не читать глазами.
- **Параллельные вызовы `data_cms_tool` из нескольких агентов путают ответы местами** — агент получает квитанцию чужого вызова (подтверждено: два `update_collection_items` обменялись ответами, `label` и id итемов не совпали с отправленными). Сами данные при этом записались верно. Мораль: по ответу конкурентного вызова ничего не проверять — перечитывать состояние отдельным запросом.
- **Формат: не всё подряд гнать в WebP.** Замерять до конвертации. Фотографии — lossy q82, выигрыш 60–95%. **Плоская графика (скриншоты, UI-макеты) в lossy WebP становится тяжелее PNG** (у нас 70К → 95К); ей нужен `lossless=True`, тогда чуть легче исходника и пиксель-в-пиксель. Логотипы 2–10 КБ не трогать вовсе — экономия единицы килобайт не стоит перезаливки. OG-картинки оставлять в jpeg: на странице они не грузятся, а скрейперы соцсетей WebP переваривают хуже.
- **Пакетная конвертация не должна звать `convert('RGB')` вслепую — это молча убивает прозрачность.** В Pillow `convert('RGB')` не «накладывает на белое», а просто выбрасывает альфа-канал, и наружу вылезает то, что лежало под ним (обычно чёрный). Проверять каждый файл до конвертации: `im.convert('RGBA').getchannel('A')` и считать пиксели с альфой < 255; если такие есть — сохранять в RGBA. Ловушка в том, что баг **точечный**: из 20 героев прозрачность была ровно у одного, остальные 19 выглядели идеально, и на общем прогоне это читается как «всё ок». После конвертации сверять число полупрозрачных пикселей в исходнике и в результате — должно совпасть (у нас 738 122 с обеих сторон). Webflow при перезаливке альфу сохраняет, так что если чёрный появился — это своя ошибка, а не CDN.
- **Webflow CDN не отдаёт WebP по content-negotiation** — заголовок `Accept: image/webp` игнорируется, приходит исходный PNG. Конвертировать нужно сами файлы, «оно само отдаст полегче» не сработает.

### `data_whtml_builder`, `set_style`-комбо, привязка переменных (гибрид-порт, подтверждено 08.2026)

Грабли, всплывшие при переносе `use-cases.html` нативными элементами (вариант B — гибрид).

- **`data_whtml_builder` = самый быстрый способ положить структуру** (целое поддерево из HTML+CSS одним вызовом, до 5 действий), но с жёсткими правилами CSS-парсера:
  - **Только одноклассовые селекторы.** Компаунд (`.filter-tab.is-on`) и потомки (`.a .b`, `.card p`) парсер **отклоняет** («Nested selectors are not allowed… StyleParser drops descendant selectors»). Всё, что компаунд/потомок (комбо-состояния, типографика на вложенных тегах), делать после — `data_style_tool` (комбо) или кастом-`<style>`.
  - **Классы, заданные в css-параметре, — литеральные значения, НЕ переменные** (`var(--…)`/токены Webflow там не резолвятся: на паблише этих CSS-переменных нет). Поэтому гибрид: whtml кладёт структуру с литералами → отдельным проходом перевязываю на Webflow-переменные (`data_style_tool` + `variable_as_value`).
  - **whtml роняет второй класс в паре «новый + существующий-глобальный».** `class="uc-card__sub paragraph-lg"` (где `uc-card__sub` определён в css, а `paragraph-lg` — глобальный) → на элемент встаёт только `uc-card__sub`, `paragraph-lg` отваливается. Одиночный существующий глобальный класс (`class="h3"`, `paragraph-sm`, `eyebrow`) резолвится в глобал **чисто**. Лечение — дособрать комбо после (см. `set_style` ниже).
  - Маппинг тегов: `<button>`→**Link** (`<a>`), `<h3>`→**Heading** (level ставится), текст-ноды сохраняются как отдельные String-узлы. UTF-8 (`Bïrch`, `—`, `“”`) не ломается — HTML entities (`&iuml;`, `&mdash;`, `&ldquo;`) отрабатывают.
- **Голый `display: grid` (без явных `grid-template-columns`) Webflow рендерит как ДВУХколоночный грид.** Обычная CSS-семантика (одна неявная колонка → стопка) тут не работает: контент, который должен стоять вертикально, встаёт в 2 колонки (у нас так «поехали» кейсы TOC, лейбл+текст промпта, голова+тело карточки). Для вертикальных стопок использовать `display: flex; flex-direction: column` (+ gap как `grid-row-gap`) или `display: block` + маргины — грид держать **только там, где он load-bearing** (напр. `grid-template-rows: 0fr↔1fr` для анимации сворачивания аккордеона; там колонок нет — одна строка). Если грид всё же нужен для раскладки — задавать `grid-template-columns` явно (`1fr`), иначе получишь 2 колонки.
- **`set_style` (data_element_tool) НЕ создаёт комбо на лету.** Он применяет только уже существующие цепочки стилей: `set_style ["uc-card","u-card-pad"]` на элемент, где комбо `.uc-card.u-card-pad` ещё нет, падает «One or more styles not found» — **даже если оба класса существуют по отдельности**. Порядок: сначала `data_style_tool > create_style` c `parent_style_names:[base]` и пустыми `properties: []` — это минтит путь `.base.combo` (пустой, но наследует свойства глобала-хвоста), — **потом** `set_style ["base","combo"]`. Так поставлены `paragraph-lg.uc-sub`, `eyebrow.uc-flush`, `uc-card.u-card-pad`.
- **`set_style` резолвит по имени и падает на неоднозначном имени.** `paragraph-sm` существует и как глобал `.paragraph-sm`, и как хвост комбо `.u-text-white.u-text-center.paragraph-sm` → `set_style ["paragraph-sm"]` = «styles not found». При этом **whtml то же имя ставит в глобал нормально**. Поэтому неоднозначные глобалы (`paragraph-sm`) вешать через whtml (пере-вставить элемент), а не `set_style`; либо сверять `styleNames` после.
- **`variable_as_value` = полная строка `variable-<uuid>`** ровно как в ответах `get_variables`/`get_styles` (напр. `"variable-abe232a6-…"`). Работает для размеров, радиусов, цветов; **гэп — только `grid-row-gap`+`grid-column-gap`** (шорткат `gap` тул не берёт). Ответ `update_style` сразу показывает, легло ли свойство как `{"id":"variable-…"}` — проверять.
- **`create_color_variable` с `custom_value:"rgba(…)"` → internal error.** Полупрозрачный цвет (hairline `#0D0D0D1F`) заводить 8-значным hex `static_value:"#RRGGBBAA"`.
- **Палитра сайта — ТЁМНАЯ; светлая тема живёт в коллекции `Theme` (моды Base/Invert).** Коллекция `Color` = `Secondary/Neutral/*` тёмного набора (White, Light Gray `#edecf2`, Mid Gray `#888680`, Dark Grey `#2a2a2a`, Black `#0b0b0b`, Background `#161616`). Наши светлые токены дизайн-системы (`surface #F1F0F7`, `muted #DBDAE2`, `text-grey #909090`, hairline) **точных Webflow-переменных не имеют** — только близкие (Light Gray ≈ surface, Mid Gray ≈ grey, Black ≈ text). Решение по проекту: переиспользовать близкие существующие, а отсутствующие (`Muted Gray #DBDAE2`, `Hairline #0D0D0D1F`) — завести. Значения брать из `tokens.css` (это синк из Figma). **Расхождение Figma↔Webflow реально** — часть акцентов тоже отличается (banner-green `#04DE00` в Figma vs `Secondary/Green #00cd36`).
- **Светлый «остров» на тёмном сайте — текст надо красить явно.** Нативные типо-классы (`h3`, `paragraph-sm`, `eyebrow`) **цвет не задают** — наследуют. На тёмном `body` наследуемый цвет светлый, поэтому на светлой карточке текст «пропадает». Ставить тёмный `color` на контейнер-остров (у нас — на `.uc-card`), дети наследуют.
- **Карточный тулинг сайта переиспользовать:** `u-card-pad` (паддинг на переменной, адаптив 32→24), шкала `_sizes---*` (rem, годится и для радиусов), токен `Card/Border Radius`. `tool-card`/`card-base` — тёмные и флекс с `gap 2rem`, под светлую grid-карточку не годятся (нужен свой лёгкий shell-класс + реюз утилит/переменных).

### Паттерн «скролл-стена карточек» (native + cqi + параллакс-колонки)

- **Скейл (шрифты тянутся с шириной):** `container-type: inline-size` на обёртке; ширину карточки диктует колонка (`width: 100%`); `font-size` на карточке — **чистый `cqi`** (напр. `3.9cqi` = 16px при дизайн-ширине 410px), **без `rem`-границ в `clamp`** — иначе fluid root-font-size Webflow ломает соотношение и перенос строк «прыгает» между брейкпоинтами. Все внутренние размеры (padding, radius, gap, иконка, кегль заголовка/описания) — в `em`. Один драйвер (ширина карточки) → всё внутри масштабируется пропорционально, JS не нужен.
- **Единый размер карточек при разном контенте:** фиксированная `height` карточки в `em` под худший кейс (напр. `18.5em` под 3-строчный заголовок + 3-строчное описание), контент по центру (`align-items/justify-content: center`), **без обрезки текста** (line-clamp не нужен; у коротких карточек просто больше цветного поля вокруг тёмной плашки).
- **Параллакс-колонки:** секция `overflow: hidden` + фикс-высота (клип, напр. `37rem`); колонки `position: absolute; top: 50%; left: 0/33.333/66.666%; width: 33.333%; transform: translateY(-50%)`. JS: `amp = (col.scrollHeight − section.clientHeight) / 2`; чередование направлений (col1 ↑, col2 ↓, col3 ↑); прогресс через `getBoundingClientRect` (не `offsetTop`); снап на первом кадре (иначе прыжок при reload); LERP-сглаживание; множитель `SPEED` c клампом target в `[-1, 1]` (быстрее без щелей по краям). Скрипт — в **Page Settings → Custom Code → Before `</body>`** (пишется через `data_scripts_tool set_page_freeform_code location:"footer"`, см. выше; ручной копипаст пользователя не нужен). Разные высоты колонок дают staircase-сдвиг сами (каждая центрируется по своей высоте).
- **Мобилка — смена оси (вертикальные колонки → горизонтальные ряды):** на узких экранах вертикальные колонки делают карточки слишком узкими (при `cqi`-кегле текст ~7px). Решение — **переиспользовать колонки как горизонтальные ряды**, DOM не трогая: на `small` (≤767) секция → `display: flex; flex-direction: column` (стек рядов, вертикальные паддинги = зазору между рядами), колонки → `position: static; flex-direction: row; width: max-content` (лента карточек), 3-ю колонку `display: none` (её контент просто не показываем на мобилке, перенос не нужен), карточке — фикс-ширина `width: min(80vw, 20rem)` (чтобы `cqi`-кегль не улетал на верхнем крае 767px), единую высоту вернуть. JS делаем **responsive по оси**: `matchMedia('(max-width:767px)')` → на мобилке `translateX` c `amp = (col.scrollWidth − section.clientWidth)/2` и центрированием `translateX(-amp + dir·cur·amp)`; на десктопе `translateY(calc(-50% + …))`. Пересчитывать режим и амплитуды на `resize`; `SPEED` держать отдельно для мобилки (горизонтальный пролёт длиннее). Скрытая колонка/ряд (`display:none`) сама выпадает — в `measure()` вернуть для неё `amp = 0`.
- **Не городить фикс-высоту + «пол шрифта» одновременно на узких экранах:** фикс-высота карточки (`18.5em`) держится только при **чистом `cqi`** (соотношение текст↔ширина как в дизайне). Если на мобилке зафлорить шрифт (`max(rem, cqi)`) при узкой карточке — текст переносится в разы больше и вылезает за фикс-высоту. Либо чистый `cqi` + фикс-высота (текст мельче, но ровно), либо `height: auto` (растёт под контент). В горизонтальных рядах ширину карточки фиксируем через `min(vw, rem)` → `cqi` стабилен → фикс-высота снова работает.
- **Проверка:** снапшот секции показывает статику; сам скролл проверяется только в Preview/стейджинге (headless-снапшот движение не покажет).

### Паттерн «scroll-driven transform на нативном Webflow-элементе» (зум/параллакс картинки)

Разделение слоёв: **база — через MCP на класс, движение — кастом-кодом** (кастом-код пишется через `data_scripts_tool set_page_freeform_code`, см. раздел про тулинг выше).

- **CSS-база через MCP** (`data_style_tool` на класс): `transform-origin` (точка привязки масштаба, напр. `bottom` — картинка «садится» нижней кромкой), `will-change: transform`. Сохраняется в Webflow, видно в Designer.
- **JS-драйвер — в Page Settings → Before `</body>`** (вставляет пользователь). Прогресс из `getBoundingClientRect()` (не `offsetTop`), снап на первом кадре, LERP-сглаживание в rAF-цикле (общие scroll-правила выше).
- **Окно анимации параметризовать через положение кромки элемента относительно viewport**, вынося точки старта/финиша в константы (`START_AT` / `FINISH_AT` как доли высоты экрана). Привязка к **верхней кромке** (`r.top`) даёт ранний старт — в отличие от центра, т.к. высокий блок закрывает пол-экрана прежде чем его центр войдёт в viewport. `START_AT > 1` — старт до появления снизу; `FINISH_AT ≤ 0` — финиш после ухода кромки за верх экрана.
- Гейт `prefers-reduced-motion: reduce` — не запускать эффект.
- **Проверка — только в Preview/на опубликованном сайте**; на канвасе Designer скролл-эффект не виден.

### Проектная заметка — высоты нава и новое меню (v2)

- **`--nav-height: 6.5em` — переменная, а не размер плашки.** Визуальный бокс боевого нава (`.nav-inner`) ≈ **5.85em** (93.6px на мобилке/1280, 112.3px при руте 19.2) — на ~10–13px короче переменной. Этот слак — тот самый «воздух», с которым sticky-блоки останавливаются под навом (пинятся они по переменной, на 6.5em). Мерить плашку и переменную раздельно; «подогнать под старый нав» значит подогнать под **переменную**.
- **Новое меню (пилл-нав) вписано в 6.5em целиком, переменная не меняется** → ни один sticky/embed не переписывается. Десктоп: воздух 6px + пилла 92px (5.75rem) + воздух 6px = 104px; мобилка: 20 + 64 + 20 = 104. Внутренние рамки пиллы параметрические: боковой инсет CTA = (высота пиллы − высота кнопки)/2, поэтому при изменении размеров симметрия пересчитывается сама. Контент пиллы стоит на сетке `.container` 80rem (лого и CTA — на краях контентной колонки).
- **Секция vision (ai-promo) после отпина уезжает под нав и на бою** — трек по живому сайту: пин на 6.5em всю фазу стека, затем −18, −218… за прозрачным навом. Прозрачное меню делает этот проезд видимым — это не баг высот; регулируется плотностью стекла.

### Проектная заметка — контент карточек стратегий на manage

Карточки стратегий на странице **Manage UPD** (`manage-upd`) берутся со **статической** (НЕ CMS) страницы `/strategies`. Там каждый пункт — `.str_frame` с `.str_h3` (заголовок), `.str_text` (описание) и `<img class="str_icon">` (иконка-SVG на CDN). **Цвет иконки-семейства задаёт цвет враппера карточки на manage** (мэппинг по префиксу имени файла иконки): `Time` → 🟢 green `#9be300`, `Pause` → 🔵 blue `#579bff`, `Scale`/`00_Scale` → 🟠 orange `#ffbf00`, `Optimise` → 🟣 violet `#9571ff` (иконки Optimise по факту пурпурно-розовые `#E965FF` — сопоставление по смыслу, не один-в-один). Исключаются семейства `Quick Start` и `Best Practices` (PNG без цвета). Плашка иконки в карточке приходит из самого SVG (в нём вшит фон-`rect`), поэтому цвет плашки совпадает с семейством автоматически.

### Опубликованная страница и page custom-code

- **Webflow page-level custom code — DOMContentLoaded** — в отличие от embed-блоков (вставляются в тело страницы через Embed-элемент), custom code заданный в настройках страницы (Page Settings → Custom Code) вставляется Webflow в `<head>`, где DOM ещё не готов. Любой такой скрипт, обращающийся к DOM (`querySelectorAll` и т.д.), оборачивать в `document.addEventListener('DOMContentLoaded', function() { ... })`. Иначе селекторы вернут пустой список и скрипт не сработает.

- **Webflow перехватывает клики по якорным `<a href="#id">` и скроллит своим jQuery-smooth — без офсета под фикс-меню** — на опубликованной Webflow-странице у любого клика по внутренней якорной ссылке срабатывает штатный обработчик Webflow: он анимирует скролл к **самому верху** целевого блока, игнорируя `scroll-margin-top` и `preventDefault` в bubble-фазе нашего кода (наш хендлер отработал, но Webflow-анимация перетёрла результат). Симптом: «анимация есть, но блок встаёт не там» — уезжает под фикс-навбар. Лечение: свой обработчик вешать на `document` в **capture-фазе** (`addEventListener('click', handler, true)`) и внутри вызывать `e.preventDefault()` + **`e.stopImmediatePropagation()`** — тогда событие вообще не доходит до Webflow-скрипта, скроллит только наш `scrollIntoView({behavior:'smooth', block:'start'})` (офсет — через `scroll-margin-top` на цели). Нюансы: (1) href при этом не отрабатывает — цель брать из `data-*`; (2) другие свои bubble-листенеры на этих же кликах тоже не сработают — их логику (напр. закрытие мобильного sheet) переносить в capture-хендлер; (3) deep-link при загрузке страницы Webflow-обработчик не трогает — но нативный прыжок браузера по хэшу происходит до присвоения JS-id, поэтому хэш обрабатывать в JS самому (открыть группу + `scrollIntoView` мгновенно, повторить на `window.load`). Подтверждено на `how-to-choose-…` (порт use-cases), 08.2026.

### Уроки порта use-cases (08.2026)

- **Источник правды зависит от типа задачи — определить в начале.** Порт готовой dev-страницы в Webflow → реплицирую dev 1:1 (Figma выше по течению; расхождения с макетом сами не всплывут - сверяться с Figma только при подозрении). Новый блок/страница без dev-версии → источник Figma, верстаю с неё напрямую.
- **freeform-правки (`set_page/site_freeform_code`) видны на сайте только после Publish.** API пишет в данные страницы, но на живой домен (bir.ch) это уходит лишь публикацией. Симптом: пишешь фикс за фиксом, а пользователь видит старое и говорит «не работает» — на самом деле смотрит непубликованную версию. Правило: после серии правок просить Publish и **статус сверять с опубликованным рендером** (curl / real Chrome), не заявлять «готово», пока не подтверждено на паблише.
- **`data_style_tool` даёт `[Conflict] ... style block store`, когда тот же класс открыт у пользователя в Designer.** Это мультиплеер-конфликт, не баг данных. Лечение: попросить закрыть/переключить класс в Designer (или обновить вкладку) и повторить запись.
- **Переиспользуемый ховер/эффект = именованный класс на элементе + правило в site-level custom-code** (`set_site_freeform_code` location `head`). Тогда `Cmd+D`/копипаст элемента на любую страницу тащит и класс, и эффект — ничего донастраивать не надо. Пример: класс `card-link` + `.card-link:hover .arrow-card-wrap img { transform: rotate(45deg) }` в site-head. Ховер на **глобальные** классы сайта (`bento-block-2`, `u-bg-lightgray`) не вешать - уедет на все страницы; вешать на свой класс-маркер. `card-link { height: 100% }` + `.card-link .bento-block-2 { height: 100% }` - чтобы карточка-ссылка тянулась на всю высоту колонки в flex-ряду.
- **Скролл на нативной Webflow-странице: `scroll-behavior` = `auto`, а плавный скролл к якорям делает jQuery-обработчик Webflow** — см. правило про перехват кликов выше. Для своего скролла — capture-фаза + `stopImmediatePropagation` + `scrollIntoView({behavior:'smooth'})`, офсет через `scroll-margin-top`.
