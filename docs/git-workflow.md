# Git в этом репозитории — когда что делать

Человеческий свод процесса: ветка → коммиты → push → PR → merge. Ядро правил живёт в `CLAUDE.md` («Git branch», «Слияние в main — только через pull request»); здесь — как они складываются в цикл, что реально запускает каждое действие и как это выглядело в истории. Визуальная версия для дизайнера — `/git-workflow guide` (файл `.claude/skills/git-workflow/guide.html`).

## Цикл одной задачи

| Шаг | Что | Команда / кнопка |
|---|---|---|
| 1 | Новая ветка под задачу, сразу выровненная на свежий ствол | Ветку создаёт сессия (в worktree — `claude/…`), но от *локального* `main`, который никто не обновляет. Поэтому первым действием, пока в ветке ноль коммитов: `git fetch origin && git merge --ff-only origin/main`. Claude делает это сам, без напоминания |
| 2 | Работа → коммиты, маленькие и про одно. Claude коммитит сам после каждого закрытого шага и сообщает одной строкой | `git add -A && git commit -m "Область: что и зачем"` |
| 3 | Push ветки, сколько угодно раз. Claude пушит сам, только свою ветку | `git push -u origin feature/<задача>` |
| 4 | **Один PR, в конце задачи, только по команде пользователя** | по фразе «оформи PR» / «слей в main»: `gh pr create --base main` + совет по способу merge. Сам Claude PR не открывает; если считает, что пора, спрашивает «оформить PR?» и ждёт |
| 5 | Ревью → Merge (обычно squash) | кнопка на GitHub; Claude сам не мержит без прямого «мержи» |
| 6 | Удалить ветку | кнопка Delete branch там же |

## Когда что делать — триггеры

| Момент | Действие | Фраза Claude |
|---|---|---|
| Новая задача / сессия | ветка уже создана сессией; Claude первым делом выравнивает её на `origin/main` (`fetch` + `merge --ff-only`) | (автоматически, «загрузи контекст» это не заменяет и не отменяет) · проверка: «на какой мы ветке?» |
| Шаг работает (блок встал, мобилка ок, правило дописано) | коммит — Claude делает сам, отчёт одной строкой | ничего; чтобы остановить: «не коммить пока» · чтобы разбить: «закоммить это отдельно» |
| Пауза, конец дня, другой Mac | push ветки — резервная копия и ссылка коллеге, `main` не трогает; Claude делает сам | ничего; «запушь ветку», если хочешь прямо сейчас |
| Задача закрыта | Claude может спросить «задача выглядит закрытой — оформить PR?» и ждёт. По команде: push + один PR, список коммитов и файлов, совет по способу merge | «оформи PR» · «слей в main» (то же самое). Без этой фразы PR не появится |
| Внутри задачи выросла неродственная фаза | свой PR на неё, когда закрыта | «это отдельная фаза — свой PR» |
| PR открыт, но есть правки | коммит + push в ту же ветку, PR обновится сам | «закоммить и запушь, PR тот же» |
| Пора нажимать Merge | решение за пользователем после совета | «согласна, squash — мержи» или кнопка на GitHub |
| Merge нажат | удалить ветку | «почисти ветку» |
| Коллега влил нужное | подтянуть `main` в ветку, чтобы не ловить конфликт в конце | «подтяни main в ветку» |
| GitHub пишет conflicts | подтянуть `main`, выбрать версии строк, закоммитить | «разбери конфликт, спроси, если не очевидно» |
| Непонятно, что произошло | ничего не удалять; всё закоммиченное восстановимо | «покажи, где мы: ветка, незакоммиченное, незапушенное» |

## Три уровня по весу

| Действие | Кто решает | Почему |
|---|---|---|
| Коммит | Claude сам | живёт в своей ветке, обратим; это Cmd+S |
| Push своей ветки | Claude сам | резервная копия на GitHub, `main` не трогает |
| PR | только пользователь | трогает общий `main`; Claude может предложить вопросом |
| Merge | только пользователь | кнопка на GitHub после совета |

## Способ merge — как выбирать

Результат в `main` одинаковый, разница только в истории.

- **Squash** — дефолт. N коммитов ветки → один коммит с названием PR. Так выглядит весь наш `main`: строка = задача. Подходит и одному коммиту, и восьмидесяти.
- **Merge commit** — когда история по коммитам ценна сама по себе: длинная многофазная работа, где потом захочется откатить один шаг, а не всю задачу. У нас ни разу не понадобился.
- **Rebase** — почти никогда. Переписывает адреса коммитов; допустим только для своей ветки, которую никто не забирал.

Перед каждым PR Claude показывает `git log main..HEAD --oneline` и `git diff --stat main..HEAD` и привязывает совет к этому списку одной фразой (правило из памяти `feedback_pr_merge_advice`).

## Как это выглядело в истории (на 02.09.2026)

- 31 PR влиты, все squash'ем: у каждого коммита `main` один родитель.
- Размер веток: от 1 коммита (правило в `CLAUDE.md`) до 85 (`claude/webflow-menu-submenu`, PR #19) и 42 (`feature/mcp-ai-use-cases`, PR #9). Коммиты внутри сессии идут пачками с интервалом 2–10 минут — по одному на закрытый шаг.
- Ветки после merge не удаляются: 19 уже влитых веток лежат на `origin`. Безопасно, но шум; закрывается кнопкой Delete branch сразу после merge.
- Главная папка на Mac стоит не на `main`, а на старой рабочей ветке, и локальный `main` никто не обновляет. Ветки живых сессий на 02.09.2026 стартовали на 2, 3, 5 и 64 коммита позади `origin/main`. Отсюда правило «сначала свежий ствол» в `CLAUDE.md`: выравнивать ветку на `origin/main` в начале каждой сессии.
- Единственный прямой push в `main` (40 коммитов fast-forward без ревью) не откатывали: переписывать общую историю хуже. Отсюда правило «только через PR».

## Нельзя

- Push в `main` мимо PR. «Слей в main» = «оформи PR».
- Коммитить на `main`. Если начали — создать ветку в любой момент до push, коммиты переедут.
- Переписывать то, что уже в `main` или у коллег: force-push, rebase `main`.
- В worktree — голый `git stash` / `git stash pop`: стек общий на все worktree. Вместо этого WIP-коммит.
