# Шрифты сайта и курсив

Что умеют шрифты bir.ch, где живут глобальные типографические правила и почему курсив включается осью, а не `font-style: italic`. Открывать перед любой работой с начертаниями, курсивом и глобальными стилями текста.

## Шрифты и их возможности

| Шрифт | Оси | Курсив |
|---|---|---|
| **TT Commons Pro Variable** (основной) | `wdth 75–125` (деф. 100), `wght 100–950` (деф. 400), `slnt 0–10` (деф. 0) | **есть, осью**: собственные Italic-инстансы шрифта сидят на `slnt 10` |
| **PPPangaia Variable** (сериф: H1 постов, дисплейные акценты) | только `wght 100–900` | **нет вообще** — ни оси, ни файла. Возможен только синтетический скос браузера |

В Webflow загружен **один** файл TT Commons Pro Variable, `@font-face` с `font-style: normal`. Отдельного italic-начертания как самостоятельного face на сайте нет — поэтому запрос `font-style: italic` браузеру приходится разруливать самому: либо крутить ось `slnt`, либо синтезировать скос. Движки решают по-разному (проверено: Chrome по ключевому слову ось **не** трогает), отсюда расхождение iOS ↔ Android.

Проверить оси любого шрифта:

```bash
curl -sL "<url .woff2 с CDN Webflow>" -o f.woff2 && python3 -c "
from fontTools.ttLib import TTFont
f=TTFont('f.woff2')
[print(a.axisTag,a.minValue,a.defaultValue,a.maxValue) for a in f['fvar'].axes]"
```

(нужен `pip install brotli` для woff2)

## Как включается курсив

Правило живёт в компоненте **Global / Fluid Type** (см. ниже):

```css
* {
  font-style: normal;
  font-weight: 600;
  font-stretch: 100%;
  font-variation-settings: "slnt" var(--slnt, 0);
}
em, i, cite, .u-italic { --slnt: 10; }
```

- **Курсив ставится тегом, а не свойством.** `<em>` покрывает CMS-rich-text и инлайновый Ctrl+I в Designer; класс `u-italic` — курсив на целом элементе. Наклон наследуется внутрь, поэтому `<strong>` внутри `<em>` получает и жир, и наклон.
- **`font-style: italic` не использовать** — ни в панели типографики Webflow, ни в CSS. Это тот самый неоднозначный путь, который расходится между движками. Он намеренно заглушён через `*`, так что в панели переключатель просто ничего не даст.
- **В серифе курсива не будет** — у PPPangaia нет оси; `--slnt: 10` там no-op. Курсив в H1 блог-поста молча не сработает, это не баг.
- **`"ital" 0` в пине не писать** — у TT Commons Pro такой оси нет. Тег-пустышка не просто бесполезен: есть подозрение, что WebKit на невалидном теге роняет всю декларацию, и тогда пин осей на iOS не применяется вовсе.

## Вес строчных элементов — наследование сломано глобальным `*`

В том же правиле стоит `font-weight: 600` на `*`. Это не дефолт, а перебивание: универсальный селектор применяется к **каждому** элементу и глушит наследование, поэтому строчный тег без класса получает 600 независимо от веса текста, в котором стоит.

Больно это именно в CMS, потому что вес на сайте пинится **по классам через ось** — в бандле 36 таких правил, например:

```css
.blogpost-rich-text p  { font-variation-settings: "wght" 500, "wdth" 100, "slnt" 0 }
.blogpost-rich-text h2 { font-variation-settings: "wdth" 89.2, "wght" 700, "slnt" 0 }
```

У `<em>` внутри такого абзаца своего класса нет: он берёт 600 из `*`, а пин `"wght" 500` с родителя до него не доезжает, потому что наше правило на `*` заменяет **весь список** `font-variation-settings`, а не дополняет его. Оба фактора складываются — курсив выходил заметно жирнее текста вокруг (репорт от 01.09.2026).

Лечится возвратом наследования:

```css
em, i, cite, a, span, sub, sup, small, mark, code, abbr, dfn, q {
  font-weight: inherit;
}
```

- **Селекторы именно элементные** — класс (0,1,0) их всегда перебивает, поэтому кнопки, ссылки-с-классом и заголовки сохраняют вес своего класса. Правило срабатывает ровно там, где класса нет, то есть в rich-text из CMS.
- **`strong` и `b` в список не добавлять** — у Webflow есть своё `b,strong{font-weight:700}` с той же специфичностью, и наше правило, идущее позже, отняло бы у них жир.
- **`a` в списке есть** (добавлен 02.09.2026 по решению дизайна): ссылка внутри текста должна весить столько же, сколько предложение вокруг неё, а не 600. Затрагивает только ссылки без класса, то есть из CMS и из текстовых блоков; кнопки и меню держатся на классах и не меняются. Замер перед выкатом: главная — 0 изменений, блог-пост — 6, `/pricing` — 6, `/use-cases` — 2.
- **Ось `wdth` этим не чинится**: `*` ставит `font-stretch: 100%`, поэтому `<em>` внутри заголовка с `wdth 89.2` будет чуть шире соседних букв. На практике незаметно, но если всплывёт — знать, откуда.

Диагностика в одну строку: сравнить в консоли `getComputedStyle(em).fontWeight` и то же у родителя. Разошлись — значит наследование перебито универсальным правилом.

## Где живут глобальные стили сайта

Fluid `html { font-size }`, `.container { max-width: 80rem }` и пин осей шрифта лежат **не** в Site Settings → Custom Code, а в embed-элементе с классом `fluid-css` внутри компонента **Global / Fluid Type** (`3d00185a-4e02-2f29-0b17-3e17b3c57f68`, группа Global). Компонент стоит на каждой странице, включая шаблон блога.

Через MCP: `data_element_settings_tool` → `get_settings` / `set_settings`, ключ `code`, с `scope_component_id` компонента. Искать через `query_elements` по странице бесполезно — элемент внутри определения компонента, нужен именно скоуп.

Плюс: embed рендерится на холсте Designer, в отличие от custom-кода страницы — дизайнер видит правку в превью.

## Исходный баг (iOS) — гипотеза

На iOS Safari весь боди-текст рендерился с наклоном, на Android — нет. Правдоподобное объяснение: CoreText подбирает **именованный инстанс** многоосевого шрифта (у TT Commons Pro их 88, половина — Italic) и без явного пина осей может выбрать италиковый. `font-style: normal` от этого не спасает — подбор идёт на этапе выбора начертания. Лечится только явными координатами осей.

Косвенное подтверждение: старый фикс лечил не `font-style`, а именно пин (`font-variation-settings` + `font-stretch`). Но пин был написан как `"ital" 0, "slnt" 0` — с несуществующей осью, что могло его обесценивать на iOS.

**Не подтверждено на устройстве.** Проверять на реальном iPhone, десктопная Safari баг не воспроизводит.

## Как проверять правки

- `debug/italic-axis-test.html` — регрессионная страница: обычный текст / `<em>` / `.u-italic` / `<strong>` внутри `<em>` / контрол с `font-style: italic`. Копия боевых правил из embed'а внутри страницы, шрифт тянется с CDN Webflow.
- **Доказать, что работает ось, а не скос**: замерить ширину одной и той же строки при `slnt 0` и `slnt 10` — у настоящего италика другие глифы, ширина отличается (у нас 1543.2 → 1547.2 при 200px). Синтетический скос ширину не меняет.
- В браузере смотреть `getComputedStyle(el).fontVariationSettings` — должно быть `"slnt" 10` на курсивных и `"slnt" 0` на остальных.
- Курсив в CMS проверять на опубликованном стейдже, а не на холсте: контент rich-text приходит из CMS.

## Публикация

У Webflow жёсткий лимит на публикацию: подряд идущие `publish_site` отдают `429 Too Many Requests`. Ретраить с паузой в несколько минут, не долбить.

## Фолбэк-метрики: как убрать сдвиг вёрстки при подмене шрифта (посчитано 25.09.2026)

**Симптом.** Пока `Tt Commons Pro Variable` грузится, текст нарисован Arial'ом, и он шире. На длинном
абзаце это незаметно, а на коротком центрированном ряду — очень: ряд табов юр-страниц в Arial шире
на **41px**, ряд отцентрован, поэтому в момент подмены он уезжает на **20,5px**.

**Важно про происхождение этих цифр.** Считались они, когда разбирались, почему прыгает ряд табов на
юр-страницах. Выяснилось, что **прыгал он не поэтому** — виноват был временный скрипт превью,
менявший подпись таба после загрузки (см. `docs/legal-versioning-plan.md`). На прогретом кэше шрифт
приезжает раньше отрисовки, и сдвига не видно. То есть **`size-adjust` ниже посчитан и проверен, но
не применён** — держим его как готовое решение на случай, когда сдвиг проявится по-настоящему
(холодный кэш, медленная связь), а не как что-то, что надо внедрять сейчас.

**Лечение — `@font-face` с `local()` и переопределёнными метриками.** Браузер берёт системный Arial,
но притворяется, что его метрики совпадают с нашими, и подмена перестаёт двигать вёрстку.

```css
@font-face {
  font-family: "TTCP fallback";
  src: local("Arial");
  font-weight: 100 550;
  size-adjust: 96.75%;
  ascent-override: 103.36%;
  descent-override: 25.84%;
  line-gap-override: 0%;
}
@font-face {
  font-family: "TTCP fallback";
  src: local("Arial");
  font-weight: 551 950;
  size-adjust: 98.60%;
  ascent-override: 101.42%;
  descent-override: 25.35%;
  line-gap-override: 0%;
}
```

Стек становится `"Tt Commons Pro Variable", "TTCP fallback", Arial, sans-serif`.

**Проверено измерением, а не расчётом:** ряд табов с фолбэк-фейсами меряется 639,6 против 639,7 у
настоящего шрифта — сдвиг центрированного ряда падает с 20,5px до 0,05px. Высота абзаца не меняется
ни в одном варианте, потому что интерлиньяж задан явно.

**Почему два фейса и почему числа не те, что даёт «честный» расчёт.** Сначала я поделил ширины
TT Commons на ширины Arial по весам и получил 97,75% и 92,81%. С ними ряд ушёл в другую сторону
(613,8 вместо 639,7). Причина: **`local("Arial")` подставляет Arial Regular**, а браузер без
переопределения брал для веса 600 настоящий Arial Bold — то есть ratio считался не против того
начертания, которое в итоге рисуется. Для 600 к Regular добавляется синтетический жир, и правильный
коэффициент оказался 98,60%, а не 92,81%. **Вывод: коэффициент подбирать итеративно по факту
отрисовки, а не делить метрики.** Скрипт подбора — в истории этой сессии, суть: меняем `size-adjust`,
меряем суммарную ширину корпуса, повторяем, пока расхождение не станет меньше 0,05%.

У Arial нет промежуточных весов: на 600 и 700 он меряется одинаково. Поэтому фейсов два — по
диапазонам весов, которые реально используются (на юр-страницах это 500 и 600).

**Что это НЕ чинит.** Текст всё равно визуально меняет форму при подмене — это FOUT, он убирается
только `font-display: optional` (ценой того, что при непрогретом кэше страница останется на Arial)
или preload'ом файла шрифта. `size-adjust` убирает **движение**, а не перерисовку.

**Ограничение по платформам.** `local("Arial")` работает там, где Arial есть: macOS, Windows, iOS. На
Android его нет, и «Arial» разрешается в Roboto с другими метриками — там числа не применимы.
Отдельная пара фейсов под Roboto считается тем же способом, но мерить надо на Android; **не сделано.**

**Это правка уровня сайта, а не раздела** — стек шрифта общий. Применять только осознанно и с
проверкой по страницам.

## Файл шрифта весит 627 КБ — и это корень проблемы с подменой (замерено 25.09.2026)

`TT_Commons_Pro_Variable.woff2` — **626,8 КБ**. Для woff2 это очень много: сабсет латиницы обычно
20–40 КБ. Именно поэтому фаза, в которой текст стоит фолбэком, длинная настолько, что её видно.

Что внутри: 1897 глифов, 1040 символов в cmap (236 кириллических, 73 греческих), три оси —
`wght 100–950`, `wdth 75–125`, `slnt 0–10`. Львиную долю занимает таблица `gvar` (1543 КБ до сжатия) —
данные вариаций по осям.

**Сколько можно снять (посчитано fontTools, не на глаз):**

| вариант | размер | экономия | что теряем |
|---|---|---|---|
| как есть | 626,8 КБ | — | — |
| только латиница, оси целы | **258,8 КБ** | −59% | кириллицу и греческий |
| + `wdth` сужен до 85–100 | **182,3 КБ** | −71% | ширины за пределами используемых |
| + `wght` сужен до 400–700 | 64,0 КБ | −90% | **нельзя** (см. ниже) |

**Что проверять перед сабсетом — здесь спрятаны грабли:**

- **Ось `wdth` используется не по умолчанию.** В CSS 33 правила её упоминают: 30 со значением `100`,
  но **два с `89.2` и одно с `86.5`**. Выкинуть ось совсем нельзя — эти три места поедут. Сужение до
  `85–100` безопасно и даёт почти тот же выигрыш.
- **Веса выходят за 400–700.** В `font-variation-settings` встречаются `170` и `806`, плюс правила
  `font-weight` со значениями 100, 200, 300 и 800. Диапазон весов сужать нельзя.
- **`slnt` обязателен** — на нём держится весь курсив сайта (см. раздел про `slnt` выше). В CSS он
  всегда `0` литералом, потому что настоящее значение приходит через `var(--slnt)`.
- **Кириллица:** на проверенных страницах (главная, блог, прайсинг, юр-страница) — ноль кириллических
  букв. Перед сабсетом прогнать по всем страницам, а не по четырём.
- **Лицензия.** TT Commons Pro — коммерческий шрифт TypeType. Сабсет для веба обычно разрешён, но это
  вопрос к EULA, и решать его не мне. **Не проверено.**

**Про `preload`: не делать, пока файл такого размера.** Механически он безопасен (две обычные грабли:
без `crossorigin` файл качается дважды, и адрес прибит гвоздями — при перезаливке шрифта preload
протухает и тянет лишние байты). Но отдавать высший приоритет самому тяжёлому файлу страницы значит
отбирать полосу у контента; на медленной связи это скорее ухудшит впечатление. После сабсета до
~180 КБ preload уже имеет смысл.
