Git для дизайнера · Birch AI

Git — это берёза.

main — ствол, который растёт у всех один. Каждая задача — ветка: отросла, поработала, вернулась в ствол. Всё остальное на этой странице — про то, как ветка растёт и как возвращается.

● main — общий ствол ● feature/… — моя ветка ● коллеги
1

Коммит — сохранённая версия с подписью

Как «Save to version history» в Figma, только подпись обязательна, и каждая версия знает свою предыдущую. Коммит живёт у тебя на компьютере, пока ты его не отправишь.

У нас

Коммит — маленький и про одно: «баннер: кегль 13px», а не «всякое». Claude пишет подпись по-русски, комментарии внутри кода — по-английски.

2

Ветка — своя копия под одну задачу

Ветка отрастает от ствола. Всё, что ты в ней делаешь, не трогает main и не мешает коллегам. Ствол тем временем растёт дальше без тебя.

У нас

Любая сессия начинается с новой ветки feature/<коротко-о-задаче>. На main напрямую не работаем никогда. У Claude каждая сессия ещё и живёт в своей папке-копии репозитория (worktree) — так две сессии не мешают друг другу.

3

Push и pull — туда и обратно

Репозиторий существует в двух местах: у тебя на Mac и на GitHub. Они не синхронизируются сами, как Figma. Ты отправляешь (push) и забираешь (pull) руками.

У нас

Push — только своей ветки: git push origin feature/…. Push в main мимо PR запрещён. Pull main — перед созданием ветки, чтобы отрасти от свежего ствола.

4

Pull request — «посмотрите и примите мою ветку»

PR — это не команда git, а страница на GitHub. На ней видно всё, что ветка меняет, можно оставить комментарии, и есть одна кнопка, которая вливает ветку в ствол.

У нас

Один PR на задачу, в конце, а не на каждый коммит. Коммиты копятся в ветке, пока задача идёт; когда закрыта — один PR. Если внутри задачи выросла отдельная неродственная фаза, у неё свой PR. Причина: PR ничего не «доставляет» на сайт (правки уже живут в Webflow), а ревью одного докового коммита — шум.

5

Три способа влить ветку в ствол

Результат в main один и тот же — файлы одинаковые. Разница только в том, как это будет выглядеть в истории потом. Вход везде один: ствол с коммитом коллеги и твоя ветка из трёх коммитов.

Squash наш дефолт

Три коммита склеиваются в один с названием PR. Ствол ровный, каждая точка на нём — одна закрытая задача. Мелкие «поправил опечатку» исчезают.

Когда: фичи, доки, всё обычное. Именно так выглядит наш main: строчка = PR.

Merge commit иногда

Ветка вливается целиком, как есть, плюс отдельный коммит-узел «слил #29». В истории видна петля: где отросла, где вернулась.

Когда: история по коммитам важна сама по себе — большая многофазная работа, где потом захочется откатить один шаг, а не всю задачу.

Rebase редко

Твои коммиты по одному «пересаживаются» на кончик ствола. Ни петли, ни склейки — прямая линия. Но это копии: у коммитов меняются адреса, история переписана.

Когда: почти никогда у нас. Переписанную историю нельзя делать с тем, что уже увидели другие.

У нас

Перед каждым PR Claude показывает список коммитов ветки и затронутые файлы и советует способ под них одной фразой. Дефолт — squash. Если советует другое, объясняет почему.

6

Одна задача от начала до конца

Цикл, который повторяется на каждую задачу. Шаги 2–3 крутятся столько раз, сколько нужно; шаг 4 — один раз.

Свежий ствол + ветка Обновить main и отрастить ветку под задачу. git checkout main
git pull
git checkout -b feature/…
Работа → коммиты Маленькие, про одно, с понятной подписью. git add -A
git commit -m "…"
Push ветки Копия ветки на GitHub. Можно много раз. git push -u origin feature/…
PR — один раз, в конце Когда задача закрыта. С советом по merge. gh pr create --base main
Ревью → Merge Кнопка на GitHub. Обычно squash. Squash and merge
Ветку удалить Она вернулась в ствол, отдельно ей делать нечего. Delete branch
Важно

Git и Webflow — две разные истории. В git живут код, embed-сниппеты и доки. Сайт живёт в Webflow, и правка там появляется в момент публикации, а не в момент merge. Поэтому PR у нас — про ревью и историю, а не про «выкатить».

7

Как это выглядело у нас

31 PR влиты в main, все squash'ем: каждая строка истории main — одна задача. Размер веток разный: от одного коммита («правило в CLAUDE.md») до 85 («меню v2», длинная сессия из многих итераций). Squash одинаково хорошо сворачивает и то и другое.

Что мы делаем не так

Ветки после merge не удаляем: 19 влитых веток всё ещё лежат на GitHub. Main-папка на Mac стоит не на main, а на старой ветке, поэтому pull main надо делать осознанно перед новой задачей. Оба пункта безопасные, но их проще закрыть привычкой, чем правилом.

8

Три вещи, которые нельзя

Всё это git разрешает технически. Запрещаем себе сами, потому что ствол общий.

нельзя Push прямо в main

Так однажды 40 коммитов уехали в main без ревью. Откатывать не стали: переписывать общую историю хуже, чем прожить с этим. «Слей в main» всегда значит «оформи PR».

нельзя Коммитить на main

Если работа началась на main — не беда: ветку можно создать в любой момент, коммиты переедут с тобой. Главное заметить до push.

нельзя Переписывать общее

Rebase и force-push допустимы только для своей ветки, которую никто ещё не забрал. Всё, что дошло до main, — уже не твоё, а общее.

9

Конфликт — это вопрос, а не поломка

Случается, когда ты и коллега поменяли одну и ту же строку в одном файле. Git не умеет выбирать за вас и просто спрашивает.
